# 06. 프론트엔드 — UX 설계 의도

Next.js 15 (App Router) · React 19 · TypeScript strict · Tailwind CSS v4 · shadcn/ui · TanStack Query · Motion. 코드는 `web/`에 있습니다.

서비스명은 **사계(SAGYE)** — 4계절 판정이라는 정체성에서 왔고 사용자가 확정했습니다. 브랜드 비주얼도 이름을 따라갑니다: 봄 코랄 → 여름 스카이 → 가을 앰버 → 겨울 인디고의 4색 그라데이션이 시그니처이고, 색 값은 `globals.css`의 `--season-*` CSS 변수가 단일 출처입니다(로고 점 4개·히어로 블롭·그라데이션 텍스트/버튼이 전부 이 변수를 참조). 판정 **결과**의 계절색은 별도로 `season-theme.ts`가 소유합니다 — 브랜드 색과 결과 색을 섞지 않기 위해서입니다.

이 문서는 화면이 "무엇을 하는지"가 아니라 **왜 이 모양인지**를 설명합니다. CLAUDE.md의 합의에 따라 UX/UI 세부는 위임받아 결정했고, 제품 성격이 갈리는 지점(시각화 비중, 인증 범위)은 사용자에게 묻고 확정했습니다.

## 1. 화면 구성

| 경로 | 역할 | 인증 |
|---|---|---|
| `/` | 업로드/웹캠 → 진행 애니메이션 → 결과 | 불필요 (로그인 시 자동 저장) |
| `/login` · `/register` | 인증. 가입 즉시 로그인 상태로 | 불필요 |
| `/history` | 내 분석 이력 (색칩 + 수치) | 필요 |
| `/history/{id}` | 저장된 분석 상세 | 필요 |

홈 화면 하나가 분석 플로우 전체를 담습니다. 별도 결과 페이지로 라우팅하지 않은 이유: 결과는 저장되지 않을 수 있어(익명 200) URL로 다시 열 수 있다는 보장이 없고, 그런 화면에 주소를 주면 새로고침이 곧 데이터 소실이 됩니다. 저장된 분석만이 `/history/{id}`라는 영속 주소를 가집니다.

## 2. 하이브리드 시각화 — 이 프로젝트 프론트의 중심 결정

전처리 단계 이미지(원본 → 화이트밸런스 → 얼굴 크롭 → 피부 마스크 → 측정 픽셀)를 어디까지 전면에 둘지가 제품 성격을 가릅니다. 세 가지를 검토해 사용자가 **하이브리드**를 택했습니다.

**결과 먼저 + 접기** — 가장 깔끔한 소비자 서비스 느낌이지만, "판정 근거를 보여준다"는 이 재구축의 정체성이 접힌 섹션 하나로 축소됩니다.

**처리 과정 전면** — 엔지니어링 쇼케이스로는 가장 강하지만, 두 번째 분석부터는 같은 애니메이션이 기다림이 됩니다.

**하이브리드 ✅** — 분석 대기 시간(1~2초)은 어차피 존재하므로 그 시간에 파이프라인 단계를 순서대로 보여주고, 완료되면 결과 카드가 주인공이 됩니다. 실제 단계 이미지 다섯 장과 보정 수치는 결과 아래 "분석 과정 자세히 보기"로 접어둡니다. 대기 시간을 교육에 쓰고, 반복 사용자에게는 방해가 되지 않습니다.

### 진행 애니메이션은 실측 진행률이 아니다

API는 요청 하나로 끝나므로 단계별 진행률을 알 방법이 없습니다. `AnalysisProgress`는 시간 기반으로 단계를 넘기다가 마지막 단계에서 응답을 기다립니다. 단계 이름은 실제 파이프라인 순서(ADR-004) 그대로지만 타이밍은 연출입니다. **화면에도 "단계 표시는 처리 순서의 안내이며 실시간 진행률은 아닙니다"라고 명시했습니다** — 측정하지 않은 것을 측정한 것처럼 보이게 하지 않는다는 저장소 전체의 태도와 같은 결입니다.

## 3. 결과 화면의 정보 순서

판정(계절 카드) → 근거(확률 분포 · 3축 게이지) → 실용(팔레트 · 팁) → 투명성(파이프라인). 위에서 아래로 "결론 → 왜 → 그래서 뭘 → 뭘 믿어도 되나"입니다.

**확률 분포는 항상 네 계절 전부** 보여줍니다(도메인 불변식 4의 UI 대응). **언더톤 신뢰도를 따로** 표시합니다 — 4계절이 애매해도 웜/쿨은 확실한 경우가 많고, 그 정보를 버리지 않습니다.

**경계 판정 안내**: `topTwoMargin < 0.15`이면 2위 계절과 확률을 명시하고 "두 계절 사이의 경계 판정"임을 알립니다. 55% vs 44%를 "55%짜리 확정"처럼 보여주는 것은 정직하지 않습니다. 0.15라는 문턱은 큐레이션이 아니라 **표현 기준**이므로 프론트가 소유합니다(`season-card.tsx`의 `BOUNDARY_MARGIN`).

**파이프라인 섹션은 보정량 공개까지가 목적**입니다. WB 게인이 1.0에 가까우면 "조명 보정이 거의 없었다"는 뜻임을 화면에서 직접 설명합니다. 이력 상세에는 이 섹션이 없는데, 버그가 아니라 단계 이미지를 저장하지 않기 때문입니다 — 원본 미저장 원칙의 자연스러운 결과입니다.

## 4. 게이트웨이 접근 — 프록시 방식 (ADR-007)

브라우저가 게이트웨이(8080)를 직접 부르지 않습니다. Next 서버의 `rewrites`가 `/api/*`를 게이트웨이로 중계해 브라우저에게는 오리진이 하나만 보입니다. CORS 설정이 통째로 사라지고, 백엔드는 프론트가 어디 배포되는지 몰라도 됩니다. 검토한 대안과 트레이드오프는 [ADR-007](07-decisions/ADR-007-frontend-integration.md)에 있습니다.

## 5. 토큰 보관 — localStorage (ADR-007)

JWT를 localStorage에 둡니다. httpOnly 쿠키 + BFF 세션이 XSS에는 더 안전하지만, **이 토큰으로 할 수 있는 일이 "내 분석 이력 읽기"뿐**이고(결제·개인정보·쓰기 권한 없음), 게이트웨이가 잘못된 토큰을 401이 아니라 익명으로 취급하므로 토큰 오염이 서비스를 막지도 못합니다. 위험 대비 BFF 복잡도가 크다고 판단했습니다. 만료(`expiresAt`)는 서버가 준 값만 믿고 **JWT를 클라이언트에서 디코드하지 않습니다** — 토큰 구조를 공개 계약으로 만들지 않기 위해서입니다.

## 6. 상태 관리 — 서버 상태만, 최소한으로

전역 클라이언트 상태 저장소(Redux 등)가 없습니다. 서버 데이터는 전부 TanStack Query가, 인증은 Context 하나(`AuthProvider`)가 담당합니다. 홈 화면의 상태 머신조차 별도로 만들지 않았습니다 — `useMutation`의 `idle/pending/success/error`가 곧 화면 상태입니다. 상태를 두 군데서 관리하기 시작하면 반드시 어긋납니다.

쿼리 키에 `userId`를 포함해 로그아웃 → 다른 계정 로그인 시 이전 사용자의 이력이 캐시에서 흘러나오지 않게 했습니다. 4xx는 재시도하지 않습니다 — 같은 요청은 같은 답을 받습니다.

## 7. 자잘하지만 의도가 있는 것들

- **업로드 전 클라이언트 축소** (최대 변 1600px): 서버도 같은 크기로 줄이므로 그 이상은 대역폭 낭비이고, 스마트폰 원본이 12MB 한도(413)에 걸리는 것을 예방합니다. 디코드 실패 시엔 원본을 그대로 보냅니다 — 서버의 `IMAGE_DECODE_FAILED` 안내가 더 정확하기 때문입니다.
- **웹캠 미리보기는 거울상, 캡처는 원본 방향**: 사용자는 거울에 익숙하지만, 캡처를 반전하면 파이프라인 시각화의 원본과 어긋납니다. 색 통계엔 좌우가 무의미하므로 캡처는 건드리지 않습니다.
- **오류 안내의 이분법**: "사진을 바꾸면 되는 실패"(422 계열)와 "서비스 문제"(503)를 다른 톤으로 안내합니다. 서킷 브레이커가 `ImageRejectedException`을 실패로 세지 않는 것과 같은 구분을 UI가 반복합니다.
- **저장 여부를 사실대로**: 응답의 `saved`를 그대로 표시합니다. 익명이면 "저장되지 않았습니다", 로그인이면 "이력에 저장되었습니다". 어느 쪽이든 "원본 사진은 저장되지 않는다"를 함께 말합니다.
- **면책 고지**: 모든 페이지 푸터에 "참고용 재미 지표이며 의료·피부과적 진단이 아닙니다"를 상시 노출합니다(CLAUDE.md 금지 사항).

## 8. 테스트

Vitest 23개. 렌더링 스냅샷이 아니라 **계약**을 고정합니다:

- 오류 매핑 — `{code, message, detail}` 보존, 계약 밖 응답(프록시 HTML 등)에서의 폴백
- 토큰 보관 — 만료·손상 데이터를 "없는 것"으로 취급하고 자가 정리
- 확률 표시 — 네 계절 전부, 내림차순 (top-1만 보여주면 실패하는 테스트)
- 경계 판정 — 마진이 작을 때만 안내가 뜨고 2위 계절이 등장

실행: `cd web && pnpm test` (lint는 `pnpm lint`, 타입은 `pnpm typecheck`)

## 9. 알려진 한계

- **E2E 테스트가 없습니다.** 실제 브라우저 플로우(업로드 → 결과)는 개발 중 수동 + 브라우저 자동화로 확인했고, Playwright 도입은 Step 6 후보입니다.
- **진행 애니메이션이 실측이 아닙니다** (§2). 실측하려면 SSE/WebSocket으로 파이프라인이 단계 이벤트를 내보내야 하는데, 무상태 원칙과 충돌해 채택하지 않았습니다.
- **다크 모드는 시스템 설정을 따르며** 수동 토글이 없습니다.
- **접근성은 기본기(시맨틱 마크업, aria-live, 키보드 포커스)까지만** 챙겼고 스크린리더 실사용 검증은 하지 않았습니다.
