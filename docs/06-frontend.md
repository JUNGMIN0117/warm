# 06. 프론트엔드 — UX 설계 의도

> Step 4 산출물. 화면이 어떻게 생겼는지가 아니라 **왜 그렇게 만들었는지**를 남긴다.
> 스택 선택의 근거는 [ADR-001](07-decisions/ADR-001-tech-stack.md), 프론트가 소비하는
> 계약은 [05-api-spec.md §10](05-api-spec.md)이 원본이다.

---

## 1. 이 프론트가 증명해야 하는 것

백엔드가 응답 설계에 들인 노력은 프론트가 보여주지 않으면 존재하지 않는 것과 같다.
게이트웨이 응답에는 확률 분포 전체, 판정 3축, 측정 수치 10여 개, 전처리 단계 이미지,
보정량 보고가 실려 있다 — 전부 "판정 결과가 아니라 판정 근거를 응답한다"는 설계의
산물이다. 그래서 이 프론트의 단일 목표는 **근거의 시각화**다. 예쁜 결과 카드는 다른
퍼스널 컬러 서비스에도 있다. 여기에만 있는 것은 "내 사진이 어떤 다섯 단계를 거쳤고,
어떤 픽셀이 측정에 쓰였고, h°가 몇이라서 웜인지"다.

이 목표에서 화면의 우선순위가 나온다. 결과 화면은 **결론 → 근거 → 과정 → 활용**
순서다. 결론(계절 카드)을 먼저 주되, 스크롤 한 번이면 확률 분포와 3축 게이지가
보인다. 근거를 아코디언 뒤에 숨기는 안을 검토했다가 기각했다 — 접힌 근거는 없는
근거와 같고, 블랙박스 탈출이 재구축의 목표였기 때문이다.

## 2. 화면 구조

```
/                업로드(드롭존·웹캠) → 분석 중 → 결과   ← 서비스의 전부가 이 한 페이지
/login /register 인증 (분석에는 불필요)
/history         이력 목록 — 색 칩 + 수치 (원본 이미지 없음)
/history/{id}    이력 상세 — 결과 화면 재사용, stages 없이
```

**랜딩 페이지를 따로 만들지 않았다.** 이 서비스가 하는 일이 곧 분석이므로, 첫
화면의 드롭존이 곧 시작점이다. 서비스 소개를 읽게 한 뒤 "시작하기" 버튼을 누르게
하는 구조는 사진 한 장 올려보려는 사용자에게 마찰만 더한다 — 익명 분석을 허용한
백엔드 결정(01-architecture §6)과 같은 방향의 결정이다.

**분석 흐름은 한 페이지 안의 상태 전이다** (idle → pending → success | error).
URL을 나누지 않은 이유: 결과에는 서버가 저장하지 않는 데이터(익명 분석,
단계 이미지)가 실려 있어 결과 페이지 URL을 만들어도 새로고침하면 사라진다.
공유 가능한 URL은 저장된 분석(`/history/{id}`)에만 의미가 있고, 그쪽에는 있다.

## 3. 핵심 UX 결정

### 가짜 진행률을 만들지 않는다

분석 API는 진행 이벤트를 주지 않는 동기 호출이다. 그럴듯한 진행률 바(3초 동안
0→90%를 채우는 애니메이션)를 넣는 안을 기각했다 — 측정하지 않은 것을 표시하지
않는다는 프로젝트 태도와 어긋난다. 대신 실제 파이프라인 5단계의 이름을 보여주며
기다리게 한다. 사용자는 진행률 대신 "지금 무슨 일이 일어나는지"를 안다.

### 경계 케이스를 단정으로 뭉개지 않는다

게이트웨이가 `topTwoMargin`을 주는 이유가 "55% vs 44%는 사실상 동점"이기
때문이다(05-api-spec §10). 프론트는 이 값이 **0.15 미만이면 단정 문구를 버리고**
"가을 웜과 봄 웜 사이입니다"로 두 계절을 병기한다. 0.15는 잠정값이며 근거와
재검토 조건은 `src/lib/verdict.ts`의 주석에 있다. 신뢰도 구간은 세 단계다:

| band | 조건 | 문구 |
|---|---|---|
| strong | 과반 + 마진 ≥ 0.15 | "~성향이 우세합니다" |
| moderate | 과반 미만 + 마진 ≥ 0.15 | "~성향이 보입니다" |
| borderline | 마진 < 0.15 | "~과 ~ 사이입니다" |

어느 문구에도 "정확도"라는 단어와 % 수치 주장이 없다. 이것은 회귀 테스트
(`verdict.test.ts`)가 고정한다 — Phase 3(수동 검증셋 평가) 전까지 정확도를
주장하지 않는 것이 저장소 전체의 금지 사항이기 때문이다.

### saved를 사실대로 보여준다

익명 분석 응답의 `saved: false`는 백엔드가 "이력에 담겼습니다"라는 거짓 안내를
막으려고 넣은 필드다. 프론트는 이를 받아 두 가지 안내로 가른다 — 저장됐으면
"원본 사진이 아니라 측정 수치만 저장됩니다", 안 됐으면 "어디에도 남지 않습니다,
이력을 원하면 가입하세요". 가입 유도조차 프라이버시 사실 위에서 한다.

### 원본을 저장하지 않는 것이 화면 구조가 된다

이력 목록에 썸네일이 없다. 서버 스키마에 이미지 컬럼이 없으므로(09-data-model)
프론트가 어떻게 하고 싶어도 불가능하다. 화면은 그 제약을 사과하는 대신 설계로
받아들인다 — 각 항목은 그때 측정된 **대표 피부색 칩**과 판정·신뢰도로 구성되고,
목록 상단에 "원본 사진은 저장되지 않습니다"를 명시한다. 제약의 이유를 화면이
직접 설명하면 제약이 기능처럼 읽힌다.

웹캠도 같은 원칙이다. 스트림은 다이얼로그가 열린 동안만 살아 있고 닫히면 즉시
모든 트랙을 멈춘다. 미리보기는 거울 모드(좌우 반전)지만 반전은 CSS 표시에만
적용된다 — 전송되는 픽셀은 원본이므로 측정에 영향이 없다.

### 오류 안내는 서버 문구를 덮어쓰지 않는다

`NO_FACE_DETECTED` 같은 422 계열의 message는 측정기(ML 서비스)가 쓴 문구가
게이트웨이를 그대로 통과해 온다. 프론트도 같은 원칙을 지킨다 — 분기는 `code`로만
하고, 본문은 서버 문구를 그대로 보여준다(`errors.test.ts`가 고정). 프론트가
추가하는 것은 "사진을 바꾸면 해결되는가"라는 분류 하나다. 해결되는 오류면
"다른 사진 선택" 버튼을, 장애(`ANALYZER_UNAVAILABLE`)면 재시도 안내를 낸다.
이 분류 기준은 서킷 브레이커가 실패를 세는 기준과 같은 축이다.

## 4. 기술 결정

### TanStack Query — 서버 상태와 클라이언트 상태의 분리

이력·분석 결과는 서버가 진실을 소유하는 데이터라 캐싱·무효화·재요청 규칙이
필요하다. 이를 useEffect + useState로 손으로 짜면 매 화면이 미니 캐시 구현이
된다. Query 훅으로 몰고, 컴포넌트는 fetch를 직접 부르지 않는 규칙을 세웠다.
분석 실행은 mutation이며 **자동 재시도를 껐다** — 서킷 브레이커가 열려 있을 때
클라이언트 재시도까지 겹치면 서버의 복구를 방해한다. 같은 사진의 중복 분석
방지도 프론트가 흉내 내지 않는다 — 서버의 Redis 캐시(이미지 해시 키)가 이미
그 일을 한다.

### JWT를 localStorage에 두는 트레이드오프

httpOnly 쿠키가 XSS에는 더 안전하다. 그럼에도 localStorage를 택한 이유:
① 게이트웨이가 Authorization 헤더 방식이라 쿠키 전환은 CORS·CSRF 설계 변경이
따라온다, ② 이 토큰이 여는 것은 "내 분석 이력 조회"가 전부라 탈취 시 피해
반경이 작다, ③ 만료 판단을 서버가 준 `expiresAt`으로만 하고 JWT를 디코드하지
않는다(디코드하는 순간 토큰 구조가 프론트와의 암묵적 계약이 된다).
**재검토 조건**: 토큰 권한이 조회를 넘어 확장되면(삭제·결제 등) 쿠키로 옮긴다.

### shadcn/ui — 그리고 Base UI 전환 함정

shadcn CLI 최신 버전(3.x)의 기본 프리셋은 Radix가 아니라 **Base UI** 기반이다.
합성 패턴이 다르다 — `asChild`가 없고 `render` prop을 쓰며, `<a>`처럼 버튼이
아닌 요소를 render에 넘길 때는 `nativeButton={false}`를 명시해야 한다.
이걸 빼면 콘솔 경고가 나고 접근성 시맨틱이 어긋난다. 문서와 검색 결과 대부분이
아직 Radix 기준이라, 기억이나 검색보다 생성된 컴포넌트 소스를 직접 읽는 것이
정확했다 (Boot 4 아티팩트명 확인과 같은 교훈).

### 3축 게이지는 채움 막대가 아니라 위치 마커

axes의 normalized(0..1)는 "많고 적음"이 아니라 "쿨↔웜 어느 쪽에 가까운가"다.
절반쯤 찬 진행률 막대로 그리면 "웜 50% 달성"처럼 오독된다. 양끝 라벨 사이의
위치 마커로 그리고, 마커 옆에 서버의 interpretation 문장과 raw 측정값을 붙였다.

## 5. 테스트 전략

UI 픽셀이 아니라 **규칙**을 테스트한다. jsdom 위에서 29개:

| 대상 | 지키는 규칙 |
|---|---|
| `verdict.test.ts` | band 분기, 55/44 동점 케이스, **정확도 주장 부재**(금지 사항 회귀) |
| `errors.test.ts` | 422 message 무가공 노출, fixable 분류 |
| `token.test.ts` | expiresAt 만료 처리, 깨진 세션 정리, JWT 미디코드 |
| `dropzone.test.ts` | 서버 계약과 같은 12MB/형식 경계 |
| `result-view.test.tsx` | 4계절 분포 전부 표시, saved 정직 안내, stages 조건부, 근거 수치 노출 |

명세의 예시 응답(05-api-spec §10)을 픽스처로 그대로 옮겼다 — 명세가 바뀌면
테스트가 깨지는 방향이 맞다. E2E(실제 게이트웨이 + ML 서비스)는 Step 6에서
Compose 위에 얹는다.

## 6. 한계 (미구현·미검증)

- **시각적 회귀 테스트가 없다.** 게이지·그라디언트가 깨져도 jsdom 테스트는 모른다.
- **웹캠 캡처는 실기기 검증 전이다.** getUserMedia 권한 거부 경로만 처리했고,
  iOS Safari의 자동재생 정책 등은 미확인.
- **`GET /seasons` 팔레트 둘러보기 화면이 없다.** 분석 없이 팔레트만 구경하는
  요구가 생기면 추가한다 — 로드맵의 Step 4 범위에는 없었다.
- **접근성은 기본 수준이다.** 게이지에 role="meter"를 붙였지만 스크린리더
  실사용 검증은 하지 않았다.
- **다크 모드 대응이 결과 카드에서 불완전하다.** 계절 그라디언트가 밝은 배경
  전제라 다크 모드에서 텍스트 색을 고정(neutral-900)했다.
