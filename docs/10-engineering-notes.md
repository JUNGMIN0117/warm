# 10. 엔지니어링 노트 — 개념 정리와 면접 대비

이 문서는 **이 프로젝트를 혼자 공부하고, 면접에서 설명하기 위한** 것입니다. 다른 문서가 "무엇을 왜 만들었는가"를 다룬다면, 여기서는 그 안에 쓰인 개념을 처음부터 설명하고 예상 질문에 어떻게 답할지 정리합니다.

> **원칙:** 모르는 것을 아는 척하지 않습니다. "아직 측정하지 않았습니다"는 감점이 아니라 가점입니다.

## 1부. 이 프로젝트 설명하기

### 30초 버전

> 2022년 대학 팀 프로젝트로 만든 퍼스널 컬러 분석기를 4년 뒤 다시 만들었습니다. 원본은 git을 안 써서 유실됐고 보고서만 남았는데, 그 보고서가 스스로 지적한 한계 세 가지를 해결하는 것이 목표였습니다. Spring Boot 게이트웨이와 Python 추론 서비스로 나눴고, 백엔드에서는 계층 경계를 빌드가 강제하도록 멀티모듈로 구성하고 외부 서비스 호출에 캐시·서킷 브레이커를 데코레이터로 얹었습니다.

### 3분 버전 — 이 순서로 말하면 됩니다

**① 문제** — 원본 보고서가 결론에 적어둔 한계 세 가지(조도 의존성, 얼굴 윤곽 학습, 라벨 오염). 자기가 만든 것의 약점을 알고 있었지만 고치지 못한 상태였습니다.

**② 접근** — 셋 다 "측정을 못 믿겠다"는 문제라, 학습 모델을 먼저 만들지 않고 **색채학 규칙 엔진을 기준선**으로 세웠습니다. 학습 데이터 0건으로 동작하고, 결과를 CIELab 좌표 세 개로 완전히 설명할 수 있고, 나중에 CNN이 정말 더 나은지 비교할 대조군이 됩니다.

**③ 구조** — 컴퓨터 비전은 Python이 압도적이고 트랜잭션·인증은 Spring이 압도적이라 나눴습니다. 경계는 **"측정된 것"과 "우리가 정한 것"** 사이에 그었습니다 — 팔레트가 Python에 있으면 색 하나 바꾸는 데 추론 서버를 재배포해야 하니까요.

**④ 백엔드에서 신경 쓴 것** — 계층 경계를 컴파일이 막게 했고, 서킷 브레이커가 "사진 문제"를 장애로 세지 않도록 했고, 원본 이미지 미저장을 스키마로 강제했습니다.

**⑤ 정직성** — 정확도를 주장하지 않습니다. 검증셋 평가 전이라 신뢰도 계수와 확률 분포로만 말합니다. 벤치마크가 제 주장을 반증했을 때는 주장을 철회했습니다.

## 2부. 개념 정리

각 항목은 **왜 필요한가 → 무엇인가 → 이 프로젝트에서 어떻게 썼는가** 순서입니다.

### 2.1 헥사고날 아키텍처 (포트와 어댑터)

**왜 필요한가.** 도메인 로직이 DB·HTTP·프레임워크에 직접 묶이면, DB를 바꾸거나 테스트를 돌릴 때마다 도메인을 건드려야 합니다. 스프링 컨텍스트를 띄우지 않으면 비즈니스 규칙 하나를 테스트할 수 없게 됩니다.

**무엇인가.** 도메인이 바깥 세계와 대화할 때 **인터페이스(포트)** 만 알게 하고, 실제 구현(어댑터)은 바깥에 두는 구조입니다. 의존 방향이 항상 안쪽(도메인)을 향합니다.

```
[바깥]  Controller  →  UseCase  →  Port(interface)
                                       ↑ implements
[바깥]                             Adapter (JPA, WebClient)
```

**이 프로젝트에서.** 포트가 다섯입니다.

| 포트 | 어댑터 | 감추는 것 |
|---|---|---|
| `PersonalColorAnalyzer` | WebClient → ML 서비스 | HTTP, 캐시, 서킷 브레이커 |
| `AnalysisRepository` | Spring Data JPA | 엔티티 매핑, 트랜잭션 |
| `SeasonProfileRepository` | Spring Data JPA | 카탈로그 스키마 |
| `UserRepository` | Spring Data JPA | 사용자 테이블 |
| `PasswordHasher` | BCrypt | 해싱 알고리즘 |

`PasswordHasher`는 두 줄짜리 위임인데도 존재합니다. 없으면 도메인이 `org.springframework.security`를 임포트하게 되고, 그 순간 도메인 순수성이 깨지기 때문입니다. 부수 이득도 있습니다 — 테스트가 실제 BCrypt(의도적으로 느린 알고리즘)를 돌리지 않아도 됩니다.

> **면접에서:** "포트를 왜 만들었나요?" → "테스트 때문만은 아니고, 캐시와 서킷 브레이커를 **데코레이터로 끼우기 위해서**입니다. 유스케이스는 자기가 캐시된 결과를 받았는지 모릅니다."

### 2.2 계층 경계를 어떻게 강제하나

**왜 필요한가.** "도메인은 프레임워크를 모른다"는 규칙은 문서에 적어두면 지켜지지 않습니다. 6개월 뒤 급한 사람이 `@Entity` 하나를 붙이고, 리뷰에서 놓치면 끝입니다.

**세 단계의 강제 수단**이 있고, 이 프로젝트는 셋 다 씁니다.

| 수단 | 언제 깨지나 | 강도 |
|---|---|---|
| 코드 리뷰·규율 | 사람이 놓치면 안 깨짐 | 약함 |
| ArchUnit 테스트 | 테스트 실행 시 | 중간 |
| **빌드 모듈 분리** | **컴파일 시** | 강함 |

**이 프로젝트에서.** `backend-domain`의 `pom.xml`에는 테스트용 ArchUnit 외에 의존성이 하나도 없습니다. 도메인에 `@Entity`를 붙이면 그 애너테이션 자체를 임포트할 수 없어 컴파일이 깨집니다.

모듈이 못 잡는 것은 ArchUnit이 맡습니다. **실제로 잡았습니다** — 컨트롤러 둘이 `SeasonProfileRepository`를 직접 주입받고 있었습니다. 규칙을 느슨하게 푸는 대신 `BrowseSeasonCatalog` 유스케이스를 만들어 고쳤습니다.

```java
noClasses()
    .that().haveSimpleNameEndingWith("Controller")
    .should().dependOnClassesThat().haveSimpleNameEndingWith("Repository")
    .because("트랜잭션 경계와 도메인 규칙을 건너뛰게 된다 — 유스케이스를 거쳐야 한다");
```

> **면접에서:** "왜 멀티모듈인가요?" → "규칙을 테스트가 잡는 것에서 컴파일이 막는 것으로 격상시키기 위해서입니다. 대가는 POM 네 개이고, 얻는 것은 도메인이 절대 오염되지 않는다는 보장입니다."

**⚠️ 함정 하나.** ArchUnit에서 `DO_NOT_INCLUDE_JARS`를 켜면 멀티모듈에서 다른 계층이 검사 대상에서 통째로 빠집니다(jar 의존성이므로). 계층 규칙을 검사하겠다면서 다른 계층을 제외하는 셈입니다. 실제로 이 실수를 했고, ArchUnit이 "검사한 클래스 없음"으로 실패시켜 준 덕에 발견했습니다.

### 2.3 서킷 브레이커 (Circuit Breaker)

**왜 필요한가.** 외부 서비스가 죽었을 때 계속 호출하면 두 가지가 나빠집니다. 매 요청이 타임아웃까지 기다려 스레드가 묶이고(연쇄 장애), 죽어가는 서비스에 부하를 더 얹습니다.

**무엇인가.** 최근 호출의 실패율을 세다가 임계치를 넘으면 **회로를 열어** 아예 호출하지 않고 즉시 실패시킵니다. 일정 시간 뒤 반개방 상태로 몇 개만 시험 호출해보고, 성공하면 닫습니다.

```
CLOSED ──실패율 초과──▶ OPEN ──대기시간 경과──▶ HALF_OPEN ──성공──▶ CLOSED
                                                      └──실패──▶ OPEN
```

**이 프로젝트에서 핵심은 "무엇을 실패로 셀 것인가"입니다.**

```java
CircuitBreakerConfig.custom()
    .failureRateThreshold(50)
    .slidingWindowSize(10)
    .waitDurationInOpenState(Duration.ofSeconds(30))
    .ignoreExceptions(ImageRejectedException.class)   // ← 이 줄이 핵심
    .build();
```

"얼굴 없는 사진"은 ML 서비스가 **정상 동작한 결과**입니다. 장애가 아닙니다. 이걸 실패로 세면 사용자가 잘못된 사진 몇 장을 올린 것만으로 회로가 열려 **정상 요청까지 막힙니다.**

그래서 예외를 두 갈래로 나눴고, 기준은 **사용자가 사진을 바꿔 고칠 수 있는가**입니다.

| 예외 | HTTP | 브레이커 |
|---|---|---|
| `ImageRejectedException` (얼굴 없음, 여러 명, 디코딩 실패) | 4xx | **무시** |
| `AnalyzerUnavailableException` (장애, 타임아웃, 회로 오픈) | 503 | 카운트 |

이 동작을 테스트로 고정했습니다 — 사진 문제를 12번 연속 던져도 회로는 `CLOSED`입니다.

> **면접에서:** "서킷 브레이커 써보셨나요?" → "네, 다만 중요한 건 임계값 설정보다 **무엇을 실패로 셀지 정하는 것**이었습니다. 사용자 입력 문제를 장애로 세면 회로가 엉뚱하게 열립니다."

**왜 애너테이션 대신 데코레이터인가.** 반은 제약, 반은 선택입니다. Resilience4j의 Spring Boot 자동설정이 아직 Boot 4를 지원하지 않고, 그 스타터가 의존하던 `spring-boot-starter-aop`가 Boot 4에서 제거됐습니다. 코어 모듈을 직접 배선한 결과 애너테이션 뒤에 숨은 동작이 코드로 드러나고, 스프링 컨텍스트 없이 단위 테스트됩니다.

### 2.4 캐시 설계 — 키가 전부입니다

**왜 캐시가 성립하나.** ML 서비스가 **무상태이고 결정론적**이기 때문입니다. 같은 이미지는 항상 같은 결과를 냅니다. 그래서 응답에 타임스탬프나 요청 id를 넣지 않습니다 — **하나만 넣어도 캐시 히트율이 0이 됩니다.**

**키 설계.**

```
pcai:analysis:{SHA-256(이미지)}:{lean|full}
```

`include_stages` 플래그가 키에 들어갑니다. 빼면 단계 이미지 없이 캐시된 응답이 시각화 요청에 반환되어 프론트가 **조용히 빈 화면**을 띄웁니다. 이 함정을 API 설계 시점에 문서에 적어뒀다가 구현할 때 처리했고, 테스트로 고정했습니다.

**데코레이터 순서.**

```
CachingAnalyzer                     ← 바깥
  └─ CircuitBreakingAnalyzer
       └─ WebClientPersonalColorAnalyzer
```

캐시가 **바깥**이어야 ML 서비스 장애 중에도 이미 아는 답은 계속 서빙됩니다. 반대로 두면 회로가 열린 동안 캐시된 결과조차 내주지 못합니다.

**캐시 장애는 요청을 실패시키지 않습니다.** Redis가 죽었을 때 분석까지 못 하게 되면 캐시가 가용성을 **낮추는** 셈입니다. 읽기·쓰기 모두 예외를 삼키고 원본 호출로 넘어갑니다.

> **면접에서:** "캐시 키는 어떻게 잡았나요?" → "이미지 해시 + 옵션 플래그입니다. 플래그를 빼면 옵션이 다른 요청에 잘못된 캐시가 나갑니다. 그리고 캐시를 서킷 브레이커 **바깥**에 뒀는데, 장애 중에도 아는 답은 서빙하기 위해서입니다."

### 2.5 JWT와 무상태 인증

**왜 필요한가.** 서버가 세션을 들고 있으면 인스턴스를 늘릴 때 세션 공유(sticky session, Redis 세션 저장소)가 필요합니다. JWT는 토큰 자체에 정보를 담고 서명으로 위조를 막아, 서버가 아무것도 기억하지 않아도 됩니다.

**구조.** `헤더.페이로드.서명` — 페이로드는 **암호화가 아니라 인코딩**입니다. 누구나 디코드해서 읽을 수 있고, 서명은 "내가 발급했다"만 보장합니다.

**이 프로젝트의 결정들.**

| 결정 | 이유 |
|---|---|
| `subject`에 이메일이 아니라 **id** | 이메일은 바뀔 수 있고 개인정보이기도 함. 토큰은 누구나 디코드 가능 |
| 리프레시 토큰 **없음** | 제대로 하려면 저장소와 폐기 목록이 필요. 로그인의 유일한 용도가 이력 조회라 그 복잡도를 감당할 이유가 없음 |
| 로그아웃 시 폐기 **없음** | 무상태 JWT의 값은 서버가 기억하지 않는 것. 폐기 목록을 두면 그 값이 사라짐. 필요해지면 세션으로 바꾸는 게 정직 |
| 서명 키 기본값 **없음** | 기본값은 그대로 배포됨. 공개 저장소에서 그것은 누구나 토큰을 위조할 수 있다는 뜻 |
| `expiresAt`을 응답에 포함 | 클라이언트가 JWT를 디코드하지 않고도 재로그인 시점을 알게. 프론트가 payload를 파싱하면 토큰 구조가 공개 계약이 됨 |

**익명 허용이 필터 설계를 바꿉니다.**

```java
// JwtAuthenticationFilter — 토큰이 없거나 잘못돼도 거절하지 않는다
bearerToken(request)
        .flatMap(jwtService::extractUserId)
        .ifPresent(userId -> SecurityContextHolder.getContext().setAuthentication(...));

chain.doFilter(request, response);   // 항상 통과시킨다
```

필터가 401을 던지면 익명 분석 흐름 자체가 막힙니다. 이 필터의 역할은 "인증 강제"가 아니라 **"있으면 알아본다"** 입니다. 판단은 인가 규칙(`authorizeHttpRequests`)에 맡깁니다.

> **면접에서:** "왜 리프레시 토큰이 없나요?" → "저장소와 폐기 목록이 필요한데, 이 서비스에서 로그인의 유일한 용도가 이력 조회라 그 복잡도가 정당화되지 않았습니다. 필요해지면 무상태를 포기하고 세션으로 바꾸는 게 정직하다고 봤습니다."

### 2.6 계정 열거(Account Enumeration) 방어

**왜 필요한가.** 로그인 실패 메시지가 "그런 계정 없음"과 "비밀번호 틀림"으로 나뉘면, 공격자가 이메일 목록을 넣어보며 **가입 여부를 수집**할 수 있습니다.

**메시지만 통일하면 부족합니다.** 계정이 없을 때 즉시 반환하면 응답 시간이 눈에 띄게 짧아져, **타이밍만으로** 같은 정보가 새어 나갑니다. BCrypt는 의도적으로 느려서(수백 ms) 차이가 큽니다.

```java
// AuthenticateUser — 없는 계정에도 더미 해시로 대조를 수행한다
Optional<User> found = users.findByEmail(normalizedEmail);
String hashToCheck = found.map(User::passwordHash).orElse(DUMMY_HASH);
boolean matched = hasher.matches(rawPassword, hashToCheck);

if (found.isEmpty() || !matched) {
    throw new InvalidCredentialsException();   // 항상 같은 예외, 같은 메시지
}
```

테스트가 이 동작을 고정합니다 — 없는 계정에도 `matches()` 호출이 정확히 1회 발생하는지 검사합니다.

**가입 화면은 반대로 알려줍니다.** "이미 가입된 이메일입니다"를 숨기면 사용자가 왜 실패하는지 알 수 없어 사용성이 크게 나빠집니다. 로그인은 숨기고 가입은 알려주는 절충입니다.

> **면접에서:** "보안 관련해서 신경 쓴 게 있나요?" → "로그인 실패를 메시지뿐 아니라 **응답 시간까지** 통일했습니다. 없는 계정에도 더미 해시로 BCrypt 대조를 한 번 돌립니다."

---

### 2.7 비밀번호 저장

**왜 해싱인가.** 평문 저장은 DB가 유출되면 끝입니다. 그리고 사람들이 비밀번호를 재사용하므로 다른 서비스까지 뚫립니다.

**왜 BCrypt인가.** SHA-256 같은 일반 해시는 **너무 빠릅니다.** GPU로 초당 수십억 번 시도할 수 있습니다. BCrypt는 의도적으로 느리고, `strength` 파라미터로 느린 정도를 조절합니다.

```java
new BCryptPasswordEncoder(12);   // 기본값 10 → 12
```

`strength`를 1 올리면 시간이 **2배**가 됩니다. 10 → 12는 4배이고, 현대 CPU에서 대략 200~300ms입니다. 로그인은 드문 연산이라 이 지연이 사용자 경험을 해치지 않으면서 오프라인 대입 공격 비용을 4배로 만듭니다.

`strength`가 해시 문자열 안에 기록되므로, 값을 바꿔도 **기존 해시는 그대로 유효합니다.**

**길이만 요구하고 구성 규칙은 없습니다.**

```java
public static final int MIN_PASSWORD_LENGTH = 10;
// 대문자·특수문자 규칙 없음
```

NIST SP 800-63B가 구성 규칙 권고를 철회했습니다. 실제로는 `Password1!` 같은 예측 가능한 패턴을 유도해 오히려 약해집니다.

**72바이트 제한.** BCrypt는 그보다 긴 입력을 **조용히 잘라냅니다.** 사용자는 긴 비밀번호를 썼다고 믿는데 실제로는 앞 72바이트만 쓰이는 상황이라, 그 전에 거절합니다.

### 2.8 트랜잭션과 `open-in-view`

**`spring.jpa.open-in-view=false`** 로 두었습니다. 기본값은 `true`인데, 그 상태에서는 요청이 끝날 때까지 영속성 컨텍스트가 열려 있어 **컨트롤러에서 지연 로딩이 조용히 동작**합니다.

문제는 두 가지입니다. 뷰 렌더링 중 예상치 못한 쿼리가 나가고(N+1의 온상), DB 커넥션을 요청 전체 시간 동안 붙잡습니다.

끄면 트랜잭션 밖에서 지연 로딩 시 `LazyInitializationException`이 납니다. **그것이 의도입니다** — 조용한 성능 저하보다 시끄러운 실패가 낫습니다.

이 프로젝트에서는 어댑터가 `@Transactional(readOnly = true)` 안에서 엔티티를 **도메인 record로 완전히 변환**하므로, 밖으로 나가는 값에 프록시가 없습니다.

```java
@Transactional(readOnly = true)
public SeasonProfile findBySeason(Season season) {
    return jpa.findById(season.code())
            .map(JpaSeasonProfileRepository::toDomain)   // 여기서 전부 변환
            .orElseThrow(() -> new SeasonProfileMissingException(season));
}
```

> **면접에서:** "`open-in-view`가 뭔지 아시나요?" → "요청 전체에 영속성 컨텍스트를 열어두는 기본 설정인데 껐습니다. 컨트롤러에서 지연 로딩이 조용히 도는 걸 막고 커넥션 점유 시간을 줄이려고요. 대신 어댑터에서 도메인 객체로 완전히 변환합니다."

### 2.9 Flyway와 `ddl-auto=validate`

**왜 마이그레이션 도구인가.** `ddl-auto=update`는 개발 중엔 편하지만 운영에서 위험합니다. 컬럼 삭제·이름 변경을 감지하지 못하고, 어떤 DDL이 실행될지 예측할 수 없으며, 롤백 경로가 없습니다.

**Flyway는 버전 있는 SQL 파일을 순서대로 한 번씩 실행하고** 이력을 `flyway_schema_history`에 남깁니다. 적용된 파일이 나중에 바뀌면 체크섬 불일치로 기동을 거부합니다.

**조합이 중요합니다.**

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate   # 스키마는 Flyway가 소유, Hibernate는 검증만
  flyway:
    enabled: true
```

`validate`는 엔티티와 실제 스키마가 어긋나면 **기동을 거부**합니다. 실제로 값을 했습니다 — `image_hash`를 `CHAR(64)`로 선언했는데 엔티티가 `varchar(64)`를 기대해 기동이 실패했고, 찾아보니 PostgreSQL의 `CHAR`는 공백 패딩을 해서 해시 저장에 부적절하기도 했습니다.

> **면접에서:** "`ddl-auto`는 뭘로 쓰셨나요?" → "`validate`입니다. 스키마 소유권은 Flyway에 두고 Hibernate는 검증만 합니다. 실제로 `CHAR` vs `VARCHAR` 불일치를 기동 시점에 잡아줬습니다."

### 2.10 테스트 전략 — 무엇을 진짜로 둘 것인가

테스트는 "무엇을 가짜로 둘 것인가"의 선택입니다. 가짜가 많을수록 빠르고, 적을수록 현실에 가깝습니다.

| 층위 | 진짜 | 가짜 | 개수 | 속도 |
|---|---|---|---|---|
| 도메인 단위 | 순수 함수 | 모든 포트 | 93 | ms |
| 어댑터 단위 | HTTP 서버(스텁) | 스프링 컨텍스트 | 18 | 초 |
| 웹 슬라이스 | Spring MVC, 보안 필터 | 유스케이스(목) | 24 | 초 |
| 영속화 통합 | **PostgreSQL 16** | ML 서비스 | 17 | 십수 초 |
| 종단 통합 | **PostgreSQL + Redis + 전체 컨텍스트** | ML 서비스(HTTP 스텁) | 16 | 십수 초 |

**왜 H2를 안 쓰나.** 스키마가 `jsonb`, 정규식 `CHECK`, `LOWER()` 함수 인덱스 같은 PostgreSQL 고유 기능에 의존합니다. H2 호환 모드로는 **마이그레이션이 통과하는지조차 확인할 수 없고**, 그러면 통합 테스트가 확인하려던 바로 그것을 확인하지 못합니다.

**Testcontainers**는 테스트 시작 시 Docker 컨테이너를 띄우고 끝나면 정리합니다. 진짜 DB를 쓰면서도 로컬 설치나 상태 오염이 없습니다.

**ML 서비스만 스텁**이고, 그것도 JDK 내장 `HttpServer`로 **진짜 HTTP 서버**를 세웁니다. 직렬화·오류 번역·타임아웃 같은 실제 실패 지점이 그대로 검증됩니다. 목 객체였다면 JSON 필드명 오타를 못 잡습니다.

**실존 인물 사진 없이 파이프라인을 테스트하는 법.** 합성 얼굴(피부색 타원 + 도형)을 만들되, **눈과 입술을 일부러 피부색으로 칠했습니다.** 색으로도 밝기로도 걸러질 수 없으니, 오직 랜드마크 폴리곤 제외만이 그 픽셀을 제거할 수 있습니다. 테스트가 검증하려는 것을 정확히 겨냥한 픽스처입니다.

> **면접에서:** "테스트는 어떻게 짜셨나요?" → "층위별로 무엇을 진짜로 둘지 정했습니다. 도메인은 전부 가짜, 통합은 진짜 PostgreSQL. H2를 안 쓴 건 스키마가 PG 고유 기능에 의존해서 호환 모드로는 검증이 안 되기 때문입니다."

### 2.11 오류 설계 — 코드와 메시지의 분리

모든 오류 응답이 같은 형태입니다.

```json
{ "code": "NO_FACE_DETECTED", "message": "얼굴을 찾지 못했습니다. …", "detail": null }
```

**`code`가 계약이고 `message`는 문구입니다.** 프론트는 코드로 분기하고 메시지는 그대로 보여줍니다. 메시지로 분기하면 문구 수정이 곧 클라이언트 파손입니다.

**메시지를 게이트웨이가 다시 쓰지 않습니다.** 실패 원인을 가장 잘 아는 쪽이 측정기이므로, "얼굴이 더 크게 나온 사진을 쓰세요" 같은 안내는 픽셀 수를 아는 쪽에서 나와야 구체적입니다.

**번역이 두 번 일어납니다.**

```
[Python] pipeline 예외 → error_mapping.py → HTTP 상태 + 코드
                                  ↓ HTTP
[Java]   MlErrorResponse → WebClient 어댑터 → 도메인 예외
                                  ↓
                    GlobalExceptionHandler → HTTP 상태 + 코드
```

낭비처럼 보이지만, 덕분에 각 계층이 자기 어휘만 씁니다. 파이프라인을 배치 작업으로 재사용해도 HTTP 상태 코드가 따라붙지 않습니다.

**403 대신 404.** 남의 분석을 요청하면 404를 줍니다. 403은 "그 id는 존재한다"를 알려주는 셈입니다.

### 2.12 컨테이너 — 레이어 캐시와 기동 순서

**왜 멀티스테이지 빌드인가.** 흔히 "이미지 크기 때문"이라고 하는데, 이 프로젝트에서 더 중요했던 것은 **캐시**입니다.

Docker는 각 명령을 레이어로 만들고, 바뀌지 않은 레이어는 재사용합니다. 그래서 **자주 바뀌는 것을 뒤에** 둬야 합니다.

```dockerfile
# backend/Dockerfile — POM을 소스보다 먼저 복사한다
COPY pom.xml ./
COPY backend-domain/pom.xml         backend-domain/
COPY backend-infrastructure/pom.xml backend-infrastructure/
COPY backend-api/pom.xml            backend-api/
RUN ./mvnw dependency:go-offline    # ← 소스가 바뀌어도 캐시에서 나옴

COPY backend-domain/src backend-domain/src   # ← 여기부터 다시 빌드
```

순서를 반대로 하면 코드 한 줄 고칠 때마다 의존성 수백 MB를 다시 받습니다.

ml-service는 스테이지를 셋으로 나눴습니다 — 의존성, 모델 다운로드, 런타임. **모델을 이미지에 구워 넣은 것은 의도적입니다.** 컨테이너가 뜰 때마다 3.7MB를 내려받으면 기동이 느려지고 네트워크 장애에 취약해집니다. 다운로드 스크립트가 SHA-256을 검증하므로 언제 빌드해도 같은 바이트가 들어갑니다.

**왜 비루트 사용자인가.** 컨테이너가 뚫렸을 때 호스트로 번지는 경로를 줄입니다. 기본값이 root라 명시하지 않으면 root로 돕니다.

```dockerfile
RUN useradd --create-home --uid 10001 appuser
USER appuser
```

**JVM 컨테이너 옵션.**

```dockerfile
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75 -XX:+UseContainerSupport"
```

이게 없으면 JVM이 **호스트 전체 메모리**를 기준으로 힙을 잡습니다. 컨테이너 한도가 512MB인데 호스트가 32GB면 힙을 8GB로 잡으려다 `OOMKilled`를 맞습니다.

**`depends_on`의 함정.**

```yaml
depends_on:
  db:
    condition: service_healthy   # service_started가 아니다
```

`service_started`는 컨테이너가 **시작됐다**는 뜻일 뿐, 그 안의 프로세스가 요청을 받을 준비가 됐다는 뜻이 아닙니다. PostgreSQL이 포트를 연 것과 쿼리를 받을 수 있는 것은 다르고, 그 사이에 Flyway가 돌면 실패합니다.

그래서 `healthcheck`를 정의하고 `condition: service_healthy`를 씁니다. `start_period`도 중요합니다 — ML 서비스는 모델 로딩에 시간이 걸려서, 이 값이 짧으면 정상 기동 중인 컨테이너가 `unhealthy`로 찍힙니다.

**노출하지 않는 것이 기본입니다.** ML 서비스에는 인증이 없으므로 호스트에 열지 않습니다. Redis도 Compose 네트워크 안에서만 쓰이므로 열지 않습니다 — 실제로 다른 프로젝트의 Redis와 6379 포트가 충돌했고, 그때 "왜 열어놨지"를 되물어 닫는 쪽으로 정리했습니다.

> **면접에서:** "Docker 최적화 해보셨나요?" → "레이어 캐시를 위해 POM을 소스보다 먼저 복사했습니다. 멀티모듈이라 POM이 넷인데, 이 순서 하나로 코드 수정 시 의존성 재다운로드를 피합니다. 그리고 `MaxRAMPercentage`를 설정했는데, 이게 없으면 JVM이 컨테이너 한도를 모르고 OOMKilled를 맞습니다."

### 2.13 CI 설계 — 무엇을 언제 검증하나

파이프라인을 네 단계로 나눴고, 순서에 이유가 있습니다.

```
ml-service (Python)  ─┐
                      ├─▶  images (이미지 빌드)  ─▶  compose (종단 기동)
backend (Java)       ─┘
```

**앞의 둘은 병렬**입니다. 서로 의존하지 않고, 하나로 합치면 "CI 실패"만 보이고 어느 서비스가 깨졌는지 로그를 열어야 합니다.

**이미지 빌드는 검증 이후**입니다. 코드가 깨진 상태의 이미지를 빌드하는 것은 러너 시간 낭비입니다.

**마지막 단계가 실질적으로 가장 강한 검증**입니다.

```yaml
run: docker compose up -d --build --wait --wait-timeout 300
```

`--wait`는 모든 헬스체크가 통과할 때까지 기다립니다. 이 한 줄로 "네 서비스가 올바른 순서로 뜨는가"가 검증되고, 이어서 실제 HTTP 호출로 DB 시드·인증·오류 처리를 확인합니다. **단위 테스트가 전부 통과해도 Compose 설정이 틀리면 여기서 잡힙니다.**

**CI에서 모델을 받지 않습니다.** MediaPipe 실추론 테스트는 모델 파일이 없으면 `skip`되도록 설계했고(`test_face_detector.py`의 `requires_model`), 실제로 모델 없이 돌리면 **102 passed, 2 skipped**입니다. 다운로드 시간과 외부 의존을 CI에서 없애면서도 나머지 회귀는 전부 잡습니다.

**`uv sync --frozen`** 을 씁니다. 락파일과 다르면 조용히 갱신하지 않고 실패합니다. CI에서 의존성이 표류하면 "로컬은 되는데 CI만 깨지는" 상황이 생깁니다.

**`concurrency` + `cancel-in-progress`** 로 같은 브랜치의 이전 실행을 취소합니다. 최신 커밋의 결과만 의미가 있습니다.

> **면접에서:** "CI는 어떻게 구성하셨나요?" → "검증을 병렬로 돌리고 그 뒤에 이미지 빌드, 마지막에 Compose 종단 기동을 넣었습니다. 마지막 단계가 핵심인데, 단위 테스트가 다 통과해도 Compose 설정이 틀리면 거기서 잡힙니다. 실제로 healthcheck `start_period`가 짧아서 정상 기동 중인 컨테이너가 unhealthy로 찍히는 문제를 그렇게 발견했습니다."

### 2.14 Spring Boot 4 마이그레이션 — 실제로 부딪힌 것들

Boot 4는 자동설정을 잘게 쪼개면서 패키지와 아티팩트가 대거 이동했습니다. **문서나 기억이 아니라 빌드를 돌려가며** 확인한 목록입니다.

| 항목 | Boot 3 | Boot 4.1 |
|---|---|---|
| 웹 스타터 | `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| 테스트 스타터 | 하나로 통합 | 기능별 분리 (`starter-webmvc-test` 등) |
| `@EntityScan` | `boot.autoconfigure.domain` | `boot.persistence.autoconfigure` |
| `@WebMvcTest` | `boot.test.autoconfigure.web.servlet` | `boot.webmvc.test.autoconfigure` |
| `TestRestTemplate` | `boot.test.web.client` | `boot.resttestclient` (별도 아티팩트) |
| AOP 스타터 | `spring-boot-starter-aop` | **제거됨** |
| **JSON** | Jackson 2 (`com.fasterxml.jackson.databind`) | **Jackson 3** (`tools.jackson.databind`) |
| Redis JSON 직렬화기 | `Jackson2JsonRedisSerializer` | `JacksonJsonRedisSerializer` |

**Jackson 3 전환이 가장 헷갈렸습니다.** `ObjectMapper`의 패키지는 바뀌었는데 **애너테이션은 여전히 `com.fasterxml.jackson.annotation`** 입니다. 그래서 `@JsonProperty`가 붙은 클래스는 멀쩡히 컴파일되는데 `ObjectMapper`를 임포트하는 순간 "package does not exist"가 납니다. **절반만 동작**하니 원인을 짚기 어렵습니다.

> **면접에서:** "왜 Boot 4를 쓰셨나요?" → "3.x가 start.spring.io에서 제공 종료됐습니다. 신규 프로젝트에 EOL 버전은 변명이 어렵죠. 대가로 생태계 지연을 겪었는데, Resilience4j 자동설정이 없어서 코어 모듈을 직접 배선했습니다."

### 2.15 프론트의 게이트웨이 접근 — rewrites 프록시

**왜 필요한가.** 브라우저(3000)가 게이트웨이(8080)를 직접 부르면 오리진이 달라 CORS가 개입합니다. 백엔드에 `allowed-origins`를 관리하는 것은 소비자의 배포 위치가 공급자 설정에 새는 결합입니다.

**무엇인가.** Next.js `rewrites`는 Next 서버가 특정 경로의 요청을 다른 주소로 중계하는 서버사이드 프록시입니다. 브라우저는 `/api/v1/...`라는 상대경로만 보고, Next 서버가 게이트웨이로 전달합니다. 오리진이 하나이므로 CORS 자체가 존재하지 않게 됩니다.

**어떻게 썼나.** `web/next.config.ts`에서 `/api/:path*` → `API_PROXY_TARGET`. 검토한 대안(직접 호출+CORS, 완전한 BFF)과 트레이드오프는 ADR-007에 있습니다.

> ⚠️ **rewrites 목적지는 빌드 타임에 고정됩니다.** `output: standalone`은 next.config를 빌드 산출물에 직렬화하므로, 컨테이너 런타임에 `API_PROXY_TARGET`을 `environment`로 넘겨도 무시됩니다. 실제로 Compose에서 이렇게 넘겼다가 기본값 `127.0.0.1:8080`으로 프록시가 500을 내서 발견했고, `--build-arg`로 굽는 방식으로 바꿨습니다. "환경변수는 런타임 설정"이라는 12-factor 직관이 Next 빌드에서는 성립하지 않는 지점입니다.

> ⚠️ **Windows + pnpm에서 standalone 빌드는 EPERM으로 죽습니다.** pnpm의 node_modules는 심볼릭 링크 구조인데, standalone 출력이 이를 복제하려면 심볼릭 링크 생성 권한(관리자 또는 개발자 모드)이 필요합니다. `BUILD_STANDALONE=1`일 때만 켜서 로컬(Windows) 빌드와 Docker(Linux) 빌드를 분리했습니다.

### 2.16 TanStack Query — 서버 상태와 클라이언트 상태의 분리

**왜 필요한가.** "서버에서 온 데이터"를 `useState`+`useEffect`로 관리하면 로딩·오류·재시도·캐시·무효화를 전부 손으로 짜게 되고, 화면마다 미묘하게 다르게 짜게 됩니다.

**무엇인가.** 서버 상태 전용 라이브러리입니다. 쿼리 키 → 비동기 함수의 쌍을 등록하면 캐시·중복 제거·백그라운드 갱신·상태 전이를 라이브러리가 소유합니다.

**어떻게 썼나.** 조회(`useQuery`)는 이력 목록·단건, 변경(`useMutation`)은 분석·로그인·가입. 세 가지 결정이 있습니다. (1) **쿼리 키에 `userId`를 포함** — 계정 전환 시 이전 사용자의 이력이 캐시에서 나오면 안 됩니다. 키가 다르면 캐시가 분리됩니다. (2) **4xx는 재시도 안 함** — 같은 요청은 같은 답을 받으므로 네트워크성 실패(5xx)만 1회 재시도합니다. (3) **분석 성공 시 `saved`면 이력 쿼리 무효화** — 서버에서 한 줄 늘었다는 사실을 클라이언트 캐시에 반영하는 표준 패턴입니다.

홈 화면에는 별도 상태 머신이 없습니다. `useMutation`의 `idle/pending/success/error`가 곧 "입력 화면/진행 애니메이션/결과/오류 안내"입니다. 상태를 두 군데서 관리하면 반드시 어긋납니다.

### 2.17 pnpm — 공급망 방어와 버전 고정

**왜 필요한가.** npm 생태계의 공격 벡터 1순위는 의존성의 `postinstall` 스크립트입니다. 설치만 해도 임의 코드가 돕니다.

**무엇인가.** pnpm 10+는 의존성의 빌드 스크립트를 **기본 차단**하고, 허용 목록(`pnpm-workspace.yaml`)에 명시한 패키지만 실행을 허용합니다. 이 프로젝트에서는 `sharp`(네이티브 이미지 라이브러리) 등 두 개만 허용했습니다.

**어떻게 썼나.** 버전 고정은 `package.json`의 `packageManager` 필드가 단일 출처입니다. Dockerfile은 `corepack enable`만 하고 버전을 적지 않으며, CI의 `pnpm/action-setup`도 버전을 적지 않습니다 — 두 군데 적으면 반드시 어긋납니다.

> ⚠️ Windows에서 `corepack enable`은 Node 설치 디렉터리(Program Files) 쓰기 권한이 없으면 EPERM으로 실패합니다. 이 경우 `npm install -g pnpm`이 사용자 디렉터리에 설치하는 우회가 됩니다.

> ⚠️ CI의 `pnpm/action-setup`은 **저장소 루트의 package.json**에서 `packageManager`를 찾습니다. 모노리포처럼 프론트가 하위 디렉터리(`web/`)에 있으면 `package_json_file: web/package.json`을 명시해야 합니다 — 실제로 이것 때문에 PR CI가 첫 실행에서 죽었습니다. 잡의 `working-directory` 기본값은 **run 스텝에만** 적용되고 액션(uses)에는 적용되지 않는다는 것이 함정의 뿌리입니다.

### 2.18 상관관계 ID — 세 서비스의 로그를 한 요청으로 꿰기

**왜 필요한가.** 한 분석 요청이 Next → Spring → FastAPI를 지난다. 장애 분석 때 "이 요청이 남긴 모든 로그"를 모으려면 세 로그에 공통 식별자가 있어야 한다. 없으면 시간대 눈짐작 대조가 유일한 수단이다.

**무엇인가.** 요청 진입 시 발급되어 모든 하류 호출과 로그에 따라다니는 ID다. 게이트웨이가 발급 주체이고(`X-Request-Id` 헤더, 유효하면 수용/아니면 발급), Java에서는 **MDC**(Mapped Diagnostic Context — 로그 라이브러리가 제공하는 스레드 로컬 키-값 저장소, 모든 로그 줄에 자동으로 붙는다)에, Python에서는 **contextvars**에 바인딩한다.

**어떻게 썼나.** Spring `RequestObservabilityFilter`(최우선 순위 — 시큐리티보다 먼저 실행돼야 401 로그에도 ID가 붙는다)가 발급·바인딩·응답 헤더 반환·완료 로그를 맡고, `CorrelationIdRelay`(WebClient 필터)가 ml-service로 전파한다. FastAPI 미들웨어가 수신·바인딩·에코를 맡는다. 프론트는 실패 화면에 이 값을 "문의 코드"로 노출한다.

> ⚠️ 두 함정을 테스트로 고정했다. (1) **MDC 정리** — 서블릿 스레드는 재사용되므로 `finally`에서 지우지 않으면 다음 요청이 남의 ID를 물려받는다. (2) **Python 스레드풀 전파** — 동기 엔드포인트는 워커 스레드에서 돌아 `threading.local`로는 미들웨어→핸들러 경로가 끊긴다. `contextvars`는 anyio가 컨텍스트를 복사해 넘겨주므로 끊기지 않는다.

> ⚠️ 헤더는 클라이언트 통제 값이다. 형식 검증(`[A-Za-z0-9._-]{8,64}`) 없이 로그에 실으면 개행 섞인 값으로 로그 파싱을 오염시킬 수 있다(로그 인젝션).

### 2.19 구조화 로그 — 텍스트는 사람이, JSON은 기계가 읽는다

**왜 필요한가.** `correlationId=X인 줄 전부`를 필드 검색하려면 로그가 구조(키-값)를 가져야 한다. 텍스트 로그는 grep까지가 한계다.

**무엇인가.** 로그 한 줄을 JSON 객체 하나로 내보내는 방식. Spring Boot 4는 내장 지원이 있어(`logging.structured.format.console=ecs`) 의존성 추가 없이 켜진다. ECS는 Elastic이 공개한 필드 이름 표준이라 수집기 매핑 설명이 필요 없다. MDC의 correlationId가 자동으로 별도 필드로 실린다.

**어떻게 썼나.** 로컬은 텍스트(사람이 읽는다), 컨테이너만 JSON(수집기가 읽는다) — docker-compose.yml이 환경변수로 켠다. Python은 표준 라이브러리 Formatter 서브클래스로 같은 원칙을 구현했다(structlog 미도입 — 필요한 것이 그보다 훨씬 작다). 요청당 완료 로그 한 줄(method·path·status·ms)을 남기되 헬스체크는 DEBUG로 낮춰 10초 간격 프로브가 로그를 도배하지 않게 했다.

### 2.20 Pseudo-label과 Grad-CAM — 대조군 실험의 도구

**왜 필요한가.** 퍼스널 컬러에는 공인 라벨이 없다. 크롤링 검색어 라벨은 오염됐고(P3), 수동 라벨은 비싸다. 그래서 규칙 엔진이 라벨을 만들고(pseudo-label) CNN이 그것을 배운다 — 이때 CNN의 성능은 정확도가 아니라 **규칙 엔진과의 일치율**이다. 이 구분이 무너지면 "82% 정확도" 같은 무의미한 수치가 문서에 스며든다(원본이 그랬다).

**Grad-CAM이 무엇인가.** 분류 근거를 시각화하는 기법 — 마지막 합성곱 층의 활성 맵에 "예측 클래스에 대한 그래디언트"를 가중해 평균하면, 모델이 판정할 때 주목한 영역의 히트맵이 나온다. 필요한 것은 forward/backward 훅 두 개와 가중 평균뿐이라 라이브러리 없이 직접 구현했다.

**어떻게 썼나.** 같은 데이터·구조·시드로 입력만 다른 두 모델(crop=윤곽 포함 / masked=피부만)을 학습해 Grad-CAM을 나란히 놓는다. crop 모델이 윤곽·배경에서 달아오르면 원본의 P2 우려("얼굴 윤곽이 학습된다")가 재현된 것이다. 모델 구조를 원본 급으로 유지한 이유도 같다 — 실험 대상은 "최고 성능"이 아니라 "원본 방식의 행동"이다.

> ⚠️ 두 가지 함정. (1) torch 2.13의 기본 ONNX 익스포터는 `onnxscript`가 별도로 필요하고, 진행 메시지에 이모지를 print해서 **Windows cp949 콘솔에서 UnicodeEncodeError로 죽는다** — 스크립트 진입 시 `sys.stdout.reconfigure(encoding="utf-8")`로 해결했다. (2) train/val 분할을 난수로 하면 실행마다 달라진다 — 파일명 해시 분할이어야 평가 스크립트가 학습과 독립적으로 같은 분할을 재현한다.

### 2.21 릴리스 게시 — "검증 통과분만 게시"라는 보증

**왜 필요한가.** 실서버 배포는 하지 않기로 했다(비용 대비 가치). 그래도 "빌드 산출물이 어디에도 발행되지 않는 CI"는 파이프라인으로서 미완이다 — 게시까지 가야 다른 사람이 소스 빌드 없이 실행해볼 수 있고, 배포가 필요해지는 순간 pull만 하면 된다.

**무엇인가.** GHCR(GitHub Container Registry)은 저장소에 붙는 컨테이너 레지스트리다. CI의 `GITHUB_TOKEN`으로 인증되므로 별도 시크릿이 없고, `permissions: packages: write`를 잡 단위로 최소 부여한다.

**어떻게 썼나.** release 잡은 **`needs: [compose]` + main 한정** — 다섯 서비스가 실제로 함께 떠서 프록시 경유 호출까지 된 커밋만 게시된다. "latest = 마지막으로 종단 검증을 통과한 조합"이라는 보증이 이 잡의 존재 이유다. 태그는 `latest`와 `sha-<커밋>` 둘 — 전자는 편의, 후자는 재현이다. 빌드 캐시는 검증(images 잡)과 같은 GHA 스코프를 읽어 방금 검증한 레이어를 재사용한다.

> ⚠️ GHCR 패키지는 **첫 게시 시 private**이다. "누구나 pull"이 되려면 저장소 Packages 설정에서 각 패키지를 한 번 public으로 바꿔야 한다 — 자동화 불가, 저장소 소유자만 가능.

## 3부. 예상 질문과 답변

### 아키텍처

**Q. 왜 서비스를 둘로 나눴나요? 모놀리스로 하면 안 되나요?**
MediaPipe의 서버사이드 Java 지원이 빈약해서입니다. 공식 Java API가 안드로이드 전제라 서버 JVM에서 돌리려면 네이티브 빌드를 직접 만져야 합니다. 얼굴 랜드마크가 전처리의 핵심이라 거기서 막히면 전체가 막힙니다. 반대로 트랜잭션·인증은 Spring이 압도적이고요. 대가는 네트워크 홉 하나와 배포 단위 둘입니다.

**Q. MSA라고 부를 수 있나요?**
아니라고 봅니다. 서비스가 둘이고 DB를 공유하지는 않지만, 독립 배포·독립 스케일링 같은 MSA의 실질적 요건을 다 갖추지는 않았습니다. "폴리글랏 2-서비스 구조"가 정확한 표현이라고 생각합니다.

**Q. 경계를 어디에 그었나요?**
"측정된 것"과 "우리가 정한 것" 사이입니다. 측정과 판정은 Python, 팔레트·라벨 같은 큐레이션은 Java+DB입니다. 판정까지 Java로 옮기는 안도 검토했는데, 34개 테스트로 검증된 로직을 이중 관리하게 되고 규칙 엔진이 모델 서빙 실패 시 폴백이어야 해서 추론 서버와 같은 프로세스에 남겼습니다.

### 성능·확장

**Q. 병목은 어디인가요?**
ML 추론입니다. 수백 ms 수준이고 CPU 바운드라, 게이트웨이 쪽 최적화는 의미가 크지 않습니다. 그래서 캐시를 이미지 해시 기준으로 걸었고, 같은 사진 재업로드는 추론을 건너뜁니다.

**Q. 수평 확장하면 어떻게 되나요?**
ML 서비스는 무상태라 자유롭게 늘릴 수 있고, 게이트웨이도 JWT 무상태라 마찬가지입니다. **다만 알려진 문제가 하나 있습니다** — 여러 게이트웨이 인스턴스가 같은 이미지를 동시에 받으면 캐시 미스가 겹쳐 ML 서비스를 중복 호출합니다. 정확성 문제는 아니라 지금은 두었고, 필요하면 분산 락이나 single-flight 패턴이 필요합니다.

**Q. 부하 테스트는 하셨나요?**
안 했습니다. 아직 실제 사진으로 종단 성능을 재보지 않았고, 그 전에 숫자를 말하는 건 의미가 없다고 봤습니다.

### 데이터

**Q. 왜 이미지를 저장하지 않나요?**
개인정보라서입니다. 보관하면 보관 기간·삭제 요청·암호화 정책이 전부 따라오는데, 얻는 가치("이력에서 원본 다시 보기")에 비해 감당할 게 많다고 판단했습니다. 대신 정책을 스키마로 강제했습니다 — 컬럼 자체가 없고, `information_schema`를 조회해 그 상태를 확인하는 테스트가 있습니다.

**Q. `analyses.season`에 FK가 없는데 의도인가요?**
의도입니다. 그 값은 "그때 이렇게 판정했다"는 역사적 스냅샷이라 카탈로그가 바뀌어도 유지돼야 합니다. 대신 애플리케이션에서 `Season.fromCode()`가 모르는 코드를 즉시 거부하고, 종단 테스트가 Python·Java·DB 세 곳의 코드 일치를 확인합니다. **다만 순수한 무결성 관점에서는 FK가 더 강하고, 계절이 4개로 고정이라 논거가 다소 이론적인 면은 있습니다.**

**Q. 인덱스는 어떤 기준으로 잡았나요?**
실제 쿼리 패턴에서 나왔습니다. 이력 조회는 항상 "내 것을, 최신순으로"라 `(user_id, analyzed_at DESC)` 복합 인덱스입니다. 순서가 중요한데, 뒤집으면 전체 스캔 후 필터가 됩니다.

### 테스트·품질

**Q. 테스트 커버리지는 얼마인가요?**
측정하지 않았습니다. 커버리지 숫자보다 "무엇을 진짜로 두고 무엇을 가짜로 둘 것인가"를 층위별로 정하는 데 집중했습니다. 다만 측정해두면 빈 곳을 찾는 데 도움이 되므로 JaCoCo 도입은 남은 일입니다.

**Q. 테스트를 짜다가 발견한 버그가 있나요?**
몇 개 있습니다. ① `ddl-auto=validate`가 `CHAR` vs `VARCHAR` 불일치를 기동 시점에 잡았습니다. ② ArchUnit이 컨트롤러의 리포지토리 직접 의존을 잡았습니다. ③ 제가 만든 테스트 격리 버그도 있었는데, `season_profiles` 삭제가 CASCADE로 팔레트까지 지우는 걸 몰라서 뒤에 도는 테스트가 깨졌습니다. `@Transactional` 롤백으로 고쳤습니다.

### 프론트엔드

**Q. JWT를 localStorage에 두면 XSS에 위험하지 않나요?**
위험합니다. 그래서 위험의 크기를 쟀습니다 — 이 토큰으로 가능한 건 자기 분석 이력 읽기뿐이고, 결제·개인정보·쓰기 권한이 없습니다. httpOnly 쿠키로 가려면 BFF 세션 계층과 CSRF 방어가 새로 필요한데, 보호 대상의 가치보다 방어 비용이 크다고 판단했습니다. 대신 토큰 접근을 파일 하나로 격리해 뒀고, 권한이 커지면 BFF로 이행한다는 재검토 조건을 ADR-007에 명시했습니다.

**Q. 왜 CORS 설정 대신 프록시인가요?**
CORS 제거는 부수 효과이고 본질은 결합 방향입니다. 백엔드가 소비자의 배포 오리진을 알아야 하는 구조를 피했습니다. ML 서비스가 자기 소비자(Spring)를 모르는 것과 같은 방향입니다.

**Q. 분석 진행률 표시는 진짜인가요?**
아닙니다. API가 요청 하나로 끝나서 단계별 진행률은 알 수 없고, 실제 파이프라인 순서를 시간 페이싱으로 보여주다 마지막 단계에서 응답을 기다립니다. 화면에도 "실시간 진행률이 아니다"라고 적어뒀습니다. 실측하려면 서버가 단계 이벤트를 스트리밍해야 하는데, 무상태 원칙과 충돌해 채택하지 않았습니다.

**Q. 프론트 테스트는 뭘 검증하나요?**
렌더링 스냅샷이 아니라 계약입니다 — 오류 응답 `{code, message}`가 보존되는가, 만료·손상 토큰이 "없는 것"으로 처리되는가, 확률이 네 계절 전부 내림차순으로 보이는가(top-1만 보여주면 실패), 경계 판정 안내가 마진 기준으로만 뜨는가. 백엔드의 도메인 불변식이 UI까지 이어지는 지점들을 골랐습니다.

### 운영·관측성

**Q. 분산 트레이싱(OpenTelemetry)을 왜 안 썼나요?**
서비스가 둘뿐이라 상관관계 ID 하나가 트레이스의 실질 가치 — 요청 단위로 로그 묶기 — 를 거의 다 줍니다. OTel은 스팬·샘플링·수집 인프라가 통째로 따라오는데, 그 비용을 지금 치를 이유가 없었습니다. 서비스가 늘거나 구간별 지연 분석이 필요해지면 traceId를 추가하는 이행 경로를 ADR-008에 남겨뒀습니다.

**Q. MDC는 스레드 로컬인데 WebClient(리액티브)에서 어떻게 안전하죠?**
좋은 지적이고, 일반적으로는 안전하지 않습니다. 이 프로젝트는 어댑터가 `.block()`으로 요청 스레드에서 구독하므로 전파 필터가 MDC를 채운 바로 그 스레드에서 실행됩니다. 이 가정을 주석과 테스트로 명시해뒀고, 완전 리액티브 전환 시 Reactor Context로 옮겨야 한다는 재검토 조건도 ADR에 있습니다.

**Q. 로그에 사용자 헤더 값을 그대로 싣는 건 위험하지 않나요?**
그래서 형식을 강제합니다. `X-Request-Id`는 `[A-Za-z0-9._-]{8,64}`에 맞을 때만 수용하고 아니면 새로 발급합니다 — 개행이 섞인 값이 로그 파싱을 오염시키는 로그 인젝션 방어입니다.

### 판단·태도

**Q. 가장 고민했던 결정은?**
파이프라인 순서입니다. 처음엔 "화이트밸런스 먼저, 검출 나중"으로 계획했는데, 합성 이미지로 검증하다가 전체 프레임 Gray-World가 **측정 대상인 피부의 웜기를 조명으로 오인해 제거**한다는 걸 발견했습니다. `b*`가 원본 27.6인데 보정 후 19.3으로 원본보다 더 내려갔습니다. 게다가 훼손 정도가 얼굴의 프레임 점유율에 비례해서, 고치려던 문제(촬영 조건 의존성)를 다른 형태로 재현하는 셈이었습니다. 순서를 뒤집고 ADR로 남겼습니다.

**Q. 실패하거나 틀린 경험이 있나요?**
있습니다. Haar Cascade를 버리는 근거로 "오검출이 많다"를 적었는데, 직접 만든 벤치마크가 재현하지 못했습니다. 벽돌·창틀·나뭇잎 등 7종에서 양쪽 다 오검출 0이었고 만화 얼굴에서는 둘 다 검출했습니다. 테스트를 원하는 답이 나올 때까지 손보는 대신 **근거를 삭제하고** 결정을 "랜드마크를 주느냐" 하나로 좁혔습니다. 그 경위도 문서에 남겼습니다.

**Q. 지금 다시 한다면 뭘 다르게 하시겠어요?**
Docker Compose를 더 일찍 만들었을 것 같습니다. Step 3까지 끝낸 뒤에 붙였는데, 그전까지는 서비스 셋을 손으로 띄워야 해서 통합 확인이 번거로웠습니다. 그리고 관측성(상관관계 ID, 구조화 로그)을 아직 미룬 게 아쉽습니다 — 나중에 넣으면 모든 로그 지점을 다시 손봐야 하니까요.

**Q. 인프라도 다뤄보셨나요?**
컨테이너화와 CI까지 했습니다. 멀티스테이지 빌드로 레이어 캐시를 설계했고, `depends_on`에 `service_healthy` 조건을 걸어 기동 순서를 보장했습니다. CI는 검증 → 이미지 빌드 → **Compose 종단 기동** 순서인데, 마지막 단계가 단위 테스트로는 못 잡는 오케스트레이션 문제를 잡습니다. 배포 파이프라인은 없습니다 — 배포할 곳이 정해지지 않아 이미지 push 단계를 만들지 않았습니다.
