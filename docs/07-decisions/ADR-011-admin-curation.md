# ADR-011. 관리자 기능 — 환경변수 부트스트랩과 큐레이션 편집

## 상태

승인됨 (2026-08-12)

## 맥락

관리자 기능 요구가 생겼다. 초기 요청은 "아이디 admin, 비밀번호 admin을 하드코딩"이었는데, 이 저장소는 "JWT 서명 키에 기본값을 두지 않는다 — 기본값은 그대로 배포된다"를 공개적으로 내세우고 있다. 공개 저장소에 admin/admin이 시드되어 있으면 그 원칙과 정면으로 모순되고, 포트폴리오 평가에서 정확히 그 지점을 지적받는다. 사용자와 논의해 방식을 바꿨다.

범위도 정했다: 관리자가 하는 일은 **계절 큐레이션 편집**(팔레트·키워드·설명·팁) 하나다. ADR-005가 "큐레이션은 재배포 없이 갱신 가능해야 한다"며 소유권을 DB로 가져왔는데, 정작 갱신 수단이 마이그레이션뿐이었다 — 이 기능이 그 약속을 완성한다.

## 검토한 선택지

### 관리자 계정

**(a) admin/admin 시드** — 기각. 위 모순에 더해, 기존 검증 규칙(이메일 형식, 비밀번호 10자+)까지 관리자만 예외로 만들어야 한다. 보안 규칙에 "관리자 예외"를 만드는 것은 최악의 방향이다.

**(b) 환경변수 부트스트랩 ✅** — `PCAI_ADMIN_EMAIL`/`PCAI_ADMIN_PASSWORD`가 설정돼 있으면 기동 시 계정을 만들거나(비밀번호 규칙은 일반 가입과 동일) 기존 계정을 승격한다. JWT 키와 같은 원칙이되 한 가지 다르다 — **없어도 기동한다.** 관리자 기능은 서비스 본체(분석)가 아니라서, 없다고 전체를 세우는 것은 과잉이다. 두 가지 세부 결정: 기존 계정의 **비밀번호는 절대 덮어쓰지 않는다**(환경변수에 남은 옛 비밀번호가 매 기동마다 변경을 되돌리는 사고 방지), 부트스트랩은 멱등이다.

**(c) 가입 API에 관리자 옵션** — 기각. 공개 API로 권한 상승 경로를 여는 셈이다.

### 권한 전달

역할을 **JWT 클레임**에 싣고 필터가 `ROLE_ADMIN` 권한으로 변환한다. 요청마다 DB를 보지 않는 무상태 원칙의 연장이며, 대가(승격/강등이 다음 로그인부터 반영)는 토큰 폐기 목록을 두지 않은 기존 트레이드오프와 같은 성질이다. role 클레임이 없는 옛 토큰은 USER로 격하된다 — 오래된 토큰이 권한을 얻는 방향의 실수가 구조적으로 불가능하다.

### 편집 저장 방식

자식 테이블(키워드·팔레트·팁)이 복합키·부모측 JoinColumn의 **조회 전용 JPA 매핑**이라, 쓰기까지 지원하게 바꾸면 insertable/updatable의 미묘함이 따라온다. 대신 **시드(V3)와 같은 형태의 명시적 SQL(DELETE+INSERT)** 로 통째로 교체한다 — "부분 수정이 아니라 교체"라는 의도가 코드에 그대로 드러나고, 잘 동작하는 조회 매핑을 건드리지 않는다.

## 결정의 부수 확인 — 캐시 무효화가 필요 없는 이유

분석 응답 캐시(Redis)에는 ml-service의 **측정 결과만** 들어 있고, 큐레이션은 응답 조립 시점에 DB에서 조인된다. 따라서 편집은 캐시를 건드리지 않고도 즉시 반영된다. ADR-005에서 그은 경계(측정 vs 큐레이션)가 여기서 공짜 이득으로 돌아온 사례다.

## 결과

- Flyway V4(`users.role`, CHECK 제약), `Role` enum, JWT role 클레임, `/api/v1/admin/** → hasRole(ADMIN)`
- `UpdateSeasonCuration` 유스케이스 (라벨·이모지는 편집 불가 — 표기 정체성)
- 프론트 `/admin` 편집 화면. role은 UI 노출 판단에만 쓰고 실제 인가는 항상 서버
- 테스트 +17 (인가 경계 401/403/200, 옛 토큰 격하, 부트스트랩 멱등·비밀번호 보존, 교체 저장 왕복)

## 재검토 조건

- 관리 기능이 둘 이상으로 늘면 → 세분화된 권한 체계 검토
- 관리자가 여러 명 필요해지면 → 부트스트랩 대신 관리자에 의한 초대 흐름
