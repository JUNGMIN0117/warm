# ADR-001. Spring Boot + FastAPI 폴리글랏 MSA

- **상태**: 채택
- **결정일**: 2026-08-07
- **관련**: ADR-002 (데이터 전략), ADR-003 (분류 범위)

---

## 맥락

원본 프로젝트는 전부 Python 단일 스크립트였고 서버가 없었습니다. 재구축에서는 웹 서비스 형태를 갖춰야 합니다.

제약 조건이 둘 있습니다.

1. **개발자의 주력 경력이 Java / Spring Boot입니다.** 이 프로젝트는 포트폴리오로도 쓰이므로, 실제 강점을 보여주지 못하는 스택 선택은 목적에 어긋납니다.
2. **컴퓨터 비전과 딥러닝 생태계는 Python이 사실상 독점입니다.** OpenCV, MediaPipe, PyTorch의 Java 대응물은 존재하더라도 문서·예제·커뮤니티가 비교 불가하게 얇습니다.

---

## 검토한 선택지

### 안 A — 순수 Python (FastAPI 단독)

원본과의 연속성이 가장 좋고 구현이 가장 빠릅니다.

**기각 사유**: Java/Spring 경력이 결과물에 전혀 드러나지 않습니다. 포트폴리오 목적을 정면으로 위배합니다.

### 안 B — 순수 Java (Spring Boot + JavaCV + DJL)

`bytedeco/javacv`가 OpenCV 전체를 Java에 바인딩하고, DJL(Deep Java Library)이 ONNX·PyTorch 모델 추론을 지원합니다. 이론적으로 100% Java가 가능합니다.

**기각 사유** — 세 가지입니다.

- **MediaPipe 서버사이드 Java 지원이 빈약합니다.** 공식 Java API는 안드로이드를 전제로 설계되어 있고, 서버 JVM에서 돌리려면 네이티브 빌드를 직접 만져야 합니다. 얼굴 랜드마크는 이 프로젝트의 핵심 전처리 단계라 여기서 막히면 전체가 막힙니다.
- **모델 학습은 어차피 Python입니다.** Java로 추론만 한다 해도 학습 파이프라인은 별도로 Python에 존재하게 됩니다. 그럴 거면 처음부터 경계를 명시적으로 긋는 편이 낫습니다.
- **전처리 로직 이식 비용이 순수 낭비입니다.** 원본의 OpenCV 코드를 JavaCV로 옮기는 작업은 새로 배우는 것도, 보여줄 것도 없는 순수 번역 노동입니다.

### 안 C — Spring Boot + FastAPI 분리 ✅

Spring Boot가 API 게이트웨이이자 도메인 서버, FastAPI가 CV/ML 추론 전용 사이드카.

## 결정

**안 C를 채택합니다.**

```
┌──────────────┐      ┌────────────────────┐      ┌──────────────────┐
│   Next.js    │─────▶│   Spring Boot 3.4  │─────▶│  FastAPI         │
│              │◀─────│   Java 21          │◀─────│  Python 3.12     │
└──────────────┘      └─────────┬──────────┘      └──────────────────┘
                                ▼
                    PostgreSQL 16  +  Redis
```

### 책임 분리

| | Spring Boot | FastAPI |
|---|---|---|
| **역할** | 도메인 · 사용자 · 이력 | 이미지 → 특징 → 판정 |
| **인증/인가** | ✅ JWT | ❌ (내부망 전용) |
| **DB 접근** | ✅ JPA | ❌ |
| **파일 업로드 수신** | ✅ | ❌ (바이트 전달받음) |
| **트랜잭션** | ✅ | ❌ (무상태) |
| **OpenCV / MediaPipe** | ❌ | ✅ |
| **모델 추론** | ❌ | ✅ ONNX Runtime |
| **팔레트 추천 로직** | ✅ | ❌ |

**FastAPI는 완전 무상태(stateless)로 유지합니다.** DB도, 인증도, 세션도 없습니다. 입력은 이미지 바이트, 출력은 JSON 특징 벡터와 판정 결과. 이 제약 덕분에 수평 확장이 자유롭고, 테스트가 단순하며, 나중에 Java(DJL)로 흡수할 때 대체 대상이 명확합니다.

## 결과

### 얻는 것

- **Java/Spring 경력이 아키텍처의 중심에 놓입니다.** 인증, 트랜잭션, JPA 모델링, WebClient 비동기 통신, Actuator 기반 헬스체크가 전부 실제로 필요한 자리에 들어갑니다.
- **CV/ML은 Python 생태계를 그대로 씁니다.** 원본 OpenCV 로직의 이식 비용이 0입니다.
- **서비스 경계 설계라는 실무 주제를 다루게 됩니다.** 타임아웃, 재시도, 서킷 브레이커, 페일오버가 억지 데모가 아니라 실제 요구사항으로 등장합니다.
- **모델을 ONNX로 표준화**해두면 나중에 DJL로 Java에 흡수하는 경로가 열려 있습니다. 이건 로드맵에 남겨두되 지금 하지는 않습니다.

### 치르는 비용

- **네트워크 홉이 하나 늘어납니다.** 이미지 바이트가 Spring → FastAPI로 한 번 더 이동합니다. 대신 원본 이미지는 FastAPI에 저장하지 않고 처리 후 폐기하므로 스토리지 부담은 없습니다.
- **로컬 개발 환경이 복잡해집니다.** Docker Compose가 선택이 아니라 필수가 됩니다.
- **장애 지점이 늘어납니다.** FastAPI가 죽으면 분석 기능 전체가 멈춥니다.

### 완화책

- Spring 측에 **Resilience4j 서킷 브레이커**를 두고, FastAPI 장애 시 즉시 실패시켜 스레드 고갈을 막습니다.
- **결과를 Redis에 캐싱**합니다. 이미지 해시를 키로 쓰면 같은 사진 재분석 시 FastAPI를 아예 호출하지 않습니다.
- FastAPI에 `/health` 엔드포인트를 두고 Spring Actuator가 이를 집계합니다.
- 서비스 간 계약을 **OpenAPI 스키마로 고정**하고, Spring 측 DTO를 여기서 생성해 드리프트를 막습니다.

## 다시 검토할 조건

- FastAPI 호출 지연이 p95 기준 800ms를 넘으면 → 전처리 일부를 Spring으로 이전 검토
- MediaPipe 서버사이드 Java 지원이 성숙하면 → 안 B 재검토
- 트래픽이 단일 인스턴스 한계를 넘으면 → 메시지 큐 기반 비동기 처리로 전환
