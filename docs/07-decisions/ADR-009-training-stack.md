# ADR-009. 학습 스택 — PyTorch + ONNX, FairFace, 언더톤 우선

## 상태

승인됨 (2026-08-11)

## 맥락

ADR-002 Phase 2(pseudo-label CNN 학습)를 실행할 도구를 골라야 했다. 결정할 것이 셋: 학습 프레임워크, 학습 데이터 출처, 기본 분류 목표.

전제가 하나 있다 — 이 CNN은 제품이 아니라 **대조군**이다. 서비스는 규칙 엔진으로 동작하고, CNN은 "원본(2022) 방식이 무엇을 학습하는가"를 관찰하는 실험 장치다. 모든 선택이 이 전제를 따른다.

## 검토한 선택지 1 — 프레임워크

**(a) TensorFlow/Keras** — 원본(2022)이 쓴 것이라 "복원" 서사에는 맞다. 그러나 Windows 네이티브 지원이 사실상 끊겼고(2.11부터 WSL 요구), 사용자 로컬이 Windows다.

**(b) PyTorch ✅** — Windows CPU 휠이 잘 관리되고, Grad-CAM에 필요한 훅 API가 일급이다. ONNX 내보내기로 프레임워크 중립 산출물을 남긴다 — Phase 3에서 CNN이 이겨 서빙이 결정되면 Java(DJL)로도, FastAPI(onnxruntime)로도 가져갈 수 있다.

**(c) scikit-learn (색채 벡터 입력)** — 이건 다른 실험이다. 색채 통계 벡터를 입력으로 쓰면 P2(공간 정보 학습) 관찰 자체가 불가능하다. 규칙 엔진의 개선판으로는 유효한 방향이지만 Phase 2의 질문에 답하지 못한다.

의존성은 `train` 그룹으로 격리했다 — **torch는 배포 이미지에 들어가지 않는다.** 서빙 코드에 모델이 등장할 이유가 생기기 전까지(Phase 3 이후) 그 경계를 유지한다.

## 검토한 선택지 2 — 데이터 출처

기준은 성능이 아니라 **라이선스의 명확성**이었다. 포트폴리오는 공개 저장소다.

FairFace(CC BY 4.0)를 골랐다. UTKFace·CelebA는 비상업/연구 한정이라 회색지대고, FFHQ는 이미지별 라이선스가 달라 검증 불가능하다. 크롤링은 ADR-002가 이미 라벨용으로 기각했다. FairFace가 인종 균형을 맞춘 구성이라는 점도 실질 이점이다 — 피부톤 분포가 넓어야 4계절 판정 문제에 의미가 있다. 상세 비교는 [02-data-pipeline.md §1](../02-data-pipeline.md).

## 검토한 선택지 3 — 기본 분류 목표

**언더톤 2분류(웜/쿨)를 기본**으로, 4계절은 옵션으로 뒀다. 원본(2022)이 푼 문제가 정확히 웜/쿨 2분류라 대조가 공정하고, pseudo-label의 잡음도 2분류가 적다(언더톤 신뢰도는 4계절 신뢰도보다 항상 높거나 같다 — 도메인 불변식 4의 귀결).

## 구현에서 의도적으로 유지한 것

- **모델 구조를 원본 급으로** (Conv 64→128→256→256 + Dense). 현대적 아키텍처로 바꾸면 "원본 방식이 무엇을 학습하는가"라는 질문이 바뀐다. BatchNorm만 추가 — 없으면 CPU 소규모 학습에서 수렴이 불안정해 관찰 이전에 학습이 안 된다.
- **증강 없음.** 색이 신호인 문제에서 color jitter는 라벨을 파괴한다.
- **train/val 분할은 파일명 해시.** 난수 대신 해시라 언제 다시 돌려도 같은 파일은 같은 쪽 — 평가 스크립트가 학습과 독립적으로 분할을 재현한다.
- **Grad-CAM 직접 구현** (훅 2개). "모델이 어디를 봤는가"를 주장하는 코드는 안이 보여야 한다.

## 결과

- `scripts/generate_pseudo_labels.py` · `train_cnn.py` · `evaluate_models.py` · `training_common.py`
- 합성 300장으로 종단 동작 검증 완료 (02-data-pipeline.md §6)
- CI는 `uv sync --group train`으로 torch까지 설치한다 — scripts/가 mypy strict 대상이라, torch 미설치면 타입이 Any로 격하되어 로컬과 CI의 검사가 갈라진다

## 재검토 조건

- Phase 3에서 CNN이 규칙 엔진을 유의미하게 이기면 → 서빙 통합 ADR을 새로 쓴다 (onnxruntime in FastAPI vs DJL in Spring)
- 학습 규모가 커져 CPU가 병목이 되면 → GPU 환경 또는 클라우드 학습 검토
