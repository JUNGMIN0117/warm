# ADR-005. 측정과 해석의 경계 — 무엇을 Python이, 무엇을 Spring이 소유하는가

- **상태**: 채택
- **결정일**: 2026-08-10
- **관련**: [ADR-001](ADR-001-tech-stack.md), [ADR-002](ADR-002-data-strategy.md), [05-api-spec.md](../05-api-spec.md)

---

## 맥락

ADR-001은 "비즈니스 로직은 Spring, 컴퓨터 비전은 Python"이라는 원칙을 세웠습니다. 그런데 Step 0에서 만든 Python 도메인 계층에는 컴퓨터 비전이 아닌 것들이 섞여 있습니다.

- `classifier.py` — 프로토타입 거리 계산. 수학이지 비전이 아닙니다.
- `seasons.py` — 계절별 추천 팔레트 48색, 한국어 라벨, 스타일링 팁. 이건 **큐레이션 결과물**이지 계산이 아닙니다.

`POST /v1/analyze`가 무엇까지 반환할지를 정하려면 이 경계를 먼저 그어야 합니다. 원칙을 문자 그대로 적용하면 분류기까지 Java로 가야 하는데, 그러면 34개 테스트로 검증된 Python 코드를 버리거나 이중 관리하게 됩니다.

---

## 검토한 선택지

### 안 A — 측정과 판정은 Python, 해석과 추천은 Spring ✅

FastAPI는 `SkinFeatures`(측정값)와 `ClassificationResult`(계절·확률·3축·신뢰도)까지 반환합니다. 반환하는 계절은 `"autumn_warm"`이라는 **enum 값**까지이고, 그것을 "🍂 가을 웜"으로 만들거나 팔레트를 붙이는 일은 Spring이 DB에서 합니다.

### 안 B — 측정만 Python, 판정 규칙까지 Java로 이식

FastAPI는 `SkinFeatures`(숫자 8개)만 반환하고, 프로토타입 거리 분류를 Java로 포팅합니다.

**기각 사유** — Java 비중이 커지는 것은 포트폴리오상 매력적이지만 대가가 큽니다. 첫째, 34개 테스트로 검증된 로직을 이중 관리하게 되고 캘리브레이션 상수가 두 곳에 존재합니다. 한쪽만 고치면 조용히 어긋나는데, 이 종류의 드리프트는 발견이 늦습니다. 둘째, ADR-002가 규칙 엔진을 **모델 서빙 실패 시의 영구 폴백**으로 규정했습니다. 폴백이 다른 프로세스에 있으면 폴백이 아닙니다. 셋째, Step 5에서 CNN과 규칙 엔진을 같은 검증셋으로 비교해야 하는데, 둘이 다른 언어·다른 프로세스에 있으면 실험 하네스가 불필요하게 복잡해집니다.

Spring의 존재감은 다른 곳에서 충분히 확보됩니다 — JWT 인증, JPA 트랜잭션, 분석 이력, Redis 캐시, Resilience4j 서킷 브레이커, 그리고 아래에서 넘겨받는 추천 도메인.

### 안 C — FastAPI가 팔레트까지 전부 반환

가장 단순합니다. Spring은 받아서 저장하고 중계만 합니다.

**기각 사유** — Spring이 CRUD 껍데기가 됩니다. 그리고 실질적인 문제가 있습니다. 팔레트는 **바뀌는 데이터**입니다. "봄 웜에 코랄 대신 살구를 넣자"는 큐레이션 판단인데, 이것이 Python 소스에 있으면 팔레트 문구 하나 고치는 데 ML 서비스를 재배포해야 합니다. 추론 서버 재배포는 모델 로딩 때문에 무겁고, 색 하나 바꾸자고 치를 비용이 아닙니다.

## 결정

**안 A를 채택합니다.** 경계는 **"측정된 것"과 "우리가 정한 것"** 사이에 긋습니다.

| | 소유 | 근거 |
|---|---|---|
| 피부 색채 통계 (L\*, a\*, b\*, C\*, h°, ITA°) | Python | 이미지에서 측정된 값 |
| 4계절 판정·확률 분포·3축 신뢰도 | Python | 측정값의 결정론적 함수. 폴백으로 제자리에 있어야 함 |
| 화이트밸런스 게인·마스킹 품질 | Python | 전처리의 부산물 |
| 계절별 팔레트·기피색 | **Spring (DB)** | 큐레이션. 재배포 없이 갱신 가능해야 함 |
| 한국어/영어 라벨·이모지·설명 | **Spring (DB)** | 프레젠테이션. 다국어 확장 지점 |
| 스타일링 팁 | **Spring (DB)** | 큐레이션 |
| 분석 이력·사용자·인증 | **Spring** | 상태. FastAPI는 무상태 유지 |

`seasons.py`는 Python에 남습니다. 규칙 엔진 폴백이 계절 정의를 필요로 하기 때문입니다. 다만 **HTTP 응답으로는 나가지 않습니다.** 큐레이션 내용은 `scripts/export_palettes.py`가 JSON으로 내보내 Step 3의 Flyway 시드가 됩니다.

두 곳의 계절 코드가 어긋나면 런타임에 "팔레트를 찾을 수 없음"이 되므로, `test_season_codes_match_palette_export`가 API 응답의 키와 시드의 `code`가 같은지 검사합니다.

### 부수 결정 1 — 응답 형태

도메인 dataclass를 그대로 직렬화하지 않고 Pydantic 스키마로 명시적으로 번역합니다. 그렇게 하지 않으면 **도메인 필드 이름을 바꾸는 순간 Spring DTO와 프론트 타입이 동시에 깨집니다.** 번역 계층이 있으면 도메인은 자유롭게 진화하고, 번역이 깨지면 mypy가 잡습니다.

확률 분포는 항상 통째로 나갑니다(도메인 불변식 4). top-1만 주면 소비자가 "62% 봄 / 35% 여름"과 "97% 겨울"을 구분할 수 없습니다.

### 부수 결정 2 — 전처리 단계 이미지는 base64 인라인

프론트의 파이프라인 시각화가 원본·WB·마스크·측정픽셀 이미지를 필요로 합니다.

**기각한 대안 — 서버 저장 후 URL 반환.** 응답은 작아지지만 **FastAPI 무상태 불변식을 깹니다.** 이미지를 어딘가 보관하는 순간 이 서비스는 저장소·만료 정책·정리 작업을 갖게 되고, 캐시 가능성과 수평 확장성이라는 무상태의 이점을 잃습니다. 전처리 시각화 편의를 위해 아키텍처의 핵심 경계를 무너뜨릴 이유가 없습니다.

**기각한 대안 — 마스크를 RLE로 보내고 프론트가 canvas에서 재구성.** 응답이 수 KB로 작아지고 인터랙티브해지지만, 감마 정확한 화이트밸런스 수학을 TypeScript에 중복 구현해야 합니다. 두 구현이 어긋나면 **사용자에게 보이는 이미지와 실제 측정에 쓰인 픽셀이 달라집니다** — 시각화의 목적이 "실제로 이 픽셀을 쟀다"를 보여주는 것인데 그게 거짓이 됩니다.

그래서 인라인으로 보내되 크기를 통제합니다. 기본 미포함(`include_stages=true`일 때만), 최대 변 512px, WebP 손실 압축. 마스크만 무손실인데, 이진 이미지를 손실 압축하면 경계에 링잉이 생겨 "어디까지가 측정 범위인가"가 흐려지기 때문입니다. 응답 상한은 테스트로 400KB에 고정했습니다.

## 결과

### 얻는 것

- 검증된 Python 도메인을 중복 없이 재사용하고, 규칙 엔진 폴백이 추론 서버와 같은 프로세스에 남습니다.
- 팔레트 큐레이션이 ML 재배포에서 분리됩니다. 색 하나 바꾸는 데 모델 서버를 건드리지 않습니다.
- Spring이 실질적인 도메인(추천·이력·인증·캐싱·회복탄력성)을 소유합니다.
- FastAPI가 무상태로 남아 Spring 쪽 이미지 해시 캐시가 성립합니다.

### 치르는 비용

- **팔레트가 두 곳에 존재하는 기간이 생깁니다.** Step 3에서 DB 시드가 완성될 때까지 `seasons.py`가 유일한 원천이고, 그 후에는 DB가 원천이며 `seasons.py`는 폴백용 사본이 됩니다. 이 이중성은 테스트로 묶어두었지만 완전히 사라지지는 않습니다.
- 응답에 `include_stages=true`를 붙이면 수백 KB가 오갑니다. Spring이 이력 저장용으로 호출할 때는 꺼야 하며, 그 판단이 호출자에게 넘어갔습니다.
- 도메인과 API 스키마 사이에 번역 코드가 생겨 필드 추가 시 두 곳을 고쳐야 합니다. 결합을 끊은 대가이며, 의도적입니다.

### 재검토 조건

- Java(DJL)로 추론까지 이식하기로 하면 안 B가 다시 살아납니다. 그때는 Python 도메인이 명세 역할을 하고 포팅 결과를 같은 테스트 케이스로 검증합니다.
- 프론트 시각화 성능이 문제가 되면 마스크 RLE 전송을 다시 봅니다. 다만 WB 이미지는 서버 렌더링을 유지해야 측정과 표시가 일치합니다.
