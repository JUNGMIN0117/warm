# ADR-008. 관측성 — 상관관계 ID의 발급 주체와 구조화 로그 형식

## 상태

승인됨 (2026-08-11)

## 맥락

한 번의 분석 요청이 세 프로세스를 지난다: Next(프록시) → Spring(게이트웨이) → FastAPI(추론). 장애가 났을 때 지금까지는 세 로그를 시간대로 눈짐작 대조하는 수밖에 없었다. "이 사용자 요청 하나가 남긴 모든 로그"를 기계적으로 모으려면 두 가지가 필요하다 — 로그를 꿰는 **실**(상관관계 ID)과, 그 실로 검색할 수 있는 **형식**(구조화 로그).

결정할 것이 셋 있었다: ID를 누가 발급하는가, 로그를 어떤 형식으로 내보내는가, 추적을 어디까지 할 것인가.

## 검토한 선택지 1 — ID 발급 주체

**(a) 프론트(브라우저)가 발급** — 사용자 행동에 가장 가깝지만, 클라이언트는 신뢰 경계 밖이다. 위조·중복·누락을 서버가 어차피 검증해야 하므로 발급 권위로 삼을 수 없다.

**(b) 게이트웨이(Spring)가 발급, 유효한 수신 값은 수용 ✅** — 모든 트래픽이 지나는 첫 신뢰 지점이다. `X-Request-Id`가 유효한 형식(`[A-Za-z0-9._-]{8,64}`)으로 들어오면 수용하고(로드밸런서·프록시가 이미 발급한 흐름을 끊지 않기 위해), 없거나 형식이 틀리면 새로 발급한다. 형식 검증은 로그 인젝션 방어를 겸한다 — 헤더는 클라이언트 통제 값이라 개행이 섞인 채 로그에 실리면 파싱이 오염된다.

**(c) 각 서비스가 독자 발급** — 서비스마다 ID가 달라져 "꿰는 실"이라는 목적 자체가 사라진다.

ML 서비스는 **발급하지 않고 수신만** 한다(헤더가 없을 때의 자체 발급은 직접 호출·테스트를 위한 안전망). 발급 주체가 둘이면 어느 ID가 권위인지가 새 문제가 된다.

## 검토한 선택지 2 — 로그 형식

**(a) 사람용 텍스트 유지** — grep은 되지만 "correlationId=X인 모든 줄"을 필드로 검색할 수 없고, 수집기(Loki·Elasticsearch 등)에 넣으려면 파싱 규칙을 별도로 관리해야 한다.

**(b) 구조화 JSON, 항상** — 검색은 되지만 로컬 개발 터미널에서 JSON 한 줄 로그는 고통스럽다.

**(c) 환경별 분리 ✅** — 로컬은 텍스트, 컨테이너는 JSON. Spring은 Boot 4 내장 구조화 로깅을 환경변수(`LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs`)로 켠다 — 의존성 추가가 0이다. 형식은 ECS(Elastic Common Schema)를 골랐다: logstash 형식과 달리 필드 이름이 공개 표준이라 수집기를 골라도 매핑 설명이 필요 없다. Python은 표준 라이브러리 `logging.Formatter` 서브클래스로 JSON을 만든다 — structlog를 넣지 않은 이유는 필요한 것이 "한 줄 = JSON 하나, request_id 포함"뿐이기 때문이다.

## 검토한 선택지 3 — 추적 범위

**분산 트레이싱(OpenTelemetry + Zipkin/Jaeger)은 이번에 하지 않는다.** 스팬·샘플링·수집 인프라가 통째로 따라오는데, 서비스가 둘뿐인 지금은 상관관계 ID 하나가 트레이스의 실질 가치(요청 단위 로그 묶기)를 거의 다 준다. 서비스가 늘거나 구간별 지연 분석이 필요해지면 그때 도입한다 — MDC 키를 그대로 두고 traceId를 추가하는 이행 경로가 있다.

## 구현이 기대는 가정 하나

WebClient 전파 필터(`CorrelationIdRelay`)는 **MDC(스레드 로컬)를 읽는다.** 리액티브 클라이언트에서 스레드 로컬은 보통 금물이지만, 이 프로젝트의 어댑터는 `.block()`으로 요청 스레드에서 구독하므로 필터 실행 스레드 = 서블릿 필터가 MDC를 채운 스레드가 보장된다. **완전 리액티브로 전환하면 이 가정이 깨진다** — 그때는 Reactor Context로 옮겨야 하며, `CorrelationIdRelayTest`가 이 동작을 고정하고 있어 깨지면 테스트가 먼저 안다.

## 결과

- 응답마다 `X-Request-Id` 헤더가 나간다. 프론트는 실패 화면에 이 값을 "문의 코드"로 노출한다 — 사용자가 불러주는 코드 하나로 세 서비스의 해당 요청 로그를 전부 찾을 수 있다
- 요청당 완료 로그 한 줄(method·path·status·소요 ms)이 게이트웨이와 ML 서비스 양쪽에 남는다. 헬스체크 프로브는 DEBUG로 낮춰 도배를 막았다
- 테스트 14개 (Java 7: 필터 5 + 전파 2 / Python 7: 미들웨어 5 + 포매터 2)

## 재검토 조건

- 완전 리액티브 전환 → MDC 가정 폐기, Reactor Context로
- 서비스 3개 이상 또는 구간별 지연 분석 필요 → OpenTelemetry 도입
- 로그 수집기 도입 → Python 포매터의 필드 이름을 수집기 스키마에 맞춰 재검토
