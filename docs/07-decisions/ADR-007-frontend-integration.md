# ADR-007. 프론트엔드 통합 — 프록시 경유 API 접근과 토큰 보관

## 상태

승인됨 (2026-08-11)

## 맥락

Step 4에서 Next.js 프론트가 Spring 게이트웨이를 소비하기 시작했다. 결정할 것이 둘 있었다.

1. **브라우저가 게이트웨이를 어떻게 부르는가** — 오리진이 다르면(3000 → 8080) CORS가 개입한다.
2. **JWT를 어디에 보관하는가** — XSS와 편의성의 오래된 트레이드오프.

## 검토한 선택지 1 — API 접근

**(a) 직접 호출 + 백엔드 CORS 설정** — 프론트가 `NEXT_PUBLIC_API_URL`로 게이트웨이를 직접 부른다. 표준적이지만 게이트웨이가 프론트의 배포 오리진을 알아야 하고(`allowed-origins` 관리), 배포 위치가 바뀔 때마다 백엔드 설정이 따라 움직인다. preflight(OPTIONS) 요청도 추가된다.

**(b) Next 서버 rewrites 프록시 ✅** — `next.config.ts`의 `rewrites`가 `/api/*`를 게이트웨이로 중계한다. 브라우저에게는 같은 오리진만 보이므로 CORS 자체가 존재하지 않는다. 게이트웨이 주소는 서버 환경변수(`API_PROXY_TARGET`) 하나로, 로컬은 `127.0.0.1:8080`, Compose에서는 `backend:8080`을 가리킨다.

**(c) Route Handler로 완전한 BFF** — Next 서버에 `/app/api/**` 핸들러를 만들어 요청을 재작성·검증까지 한다. 토큰을 httpOnly 쿠키 세션으로 바꿀 수 있는 유일한 구조지만, 사실상 게이트웨이 앞에 게이트웨이를 하나 더 짓는 것이다. 이 프로젝트의 백엔드 서사는 Spring에 있어야 한다 — 같은 역할의 계층을 Node에 복제하면 포트폴리오의 초점이 흐려진다.

### 결정: (b) rewrites 프록시

CORS 제거는 부수 효과이고, 본질적 이득은 **결합 방향**이다. 백엔드는 소비자의 배포 위치를 모르는 채로 남고, 프론트만 자신의 데이터 출처를 안다. ML 서비스가 자신의 소비자(Spring)를 모르는 것과 같은 방향의 의존이다.

비용도 있다: 프론트 서버가 모든 API 트래픽의 경유지가 되므로 web 컨테이너가 죽으면 API도 못 쓴다. 정적 export(`output: export`)도 포기한다 — rewrites는 Node 서버가 있어야 동작한다. 둘 다 수용했다. 어차피 SSR을 쓰고, 단일 진입점은 운영 관점에서 오히려 단순하다.

## 검토한 선택지 2 — 토큰 보관

**(a) httpOnly 쿠키 + BFF 세션** — XSS로 토큰을 탈취할 수 없는 유일한 방식. 그러나 선택지 1-(c)를 강제하고, CSRF 방어가 새로 필요해진다(쿠키는 자동 전송되므로).

**(b) localStorage ✅** — XSS에 토큰이 노출된다. 그 위험을 **토큰의 권한 크기**와 견줬다: 이 토큰으로 가능한 것은 자기 분석 이력 읽기뿐이다. 결제 수단도, 개인정보 수정도, 타인 데이터 접근도 없다(남의 이력은 404). 잘못된 토큰은 게이트웨이가 익명으로 취급하므로 오염된 토큰이 서비스를 막지도 못한다. 방어 비용이 보호 대상의 가치를 넘는다고 판단했다.

**(c) 메모리 전용(새로고침마다 재로그인)** — 가장 안전하지만 "이력 보려고 매번 로그인"은 이 서비스의 마찰 허용치를 넘는다.

### 결정: (b) localStorage

단, 두 가지 규율을 함께 둔다. **JWT를 클라이언트에서 디코드하지 않는다** — 만료 판단은 서버가 준 `expiresAt`으로만 한다(토큰 내부 구조를 공개 계약으로 만들지 않기 위해). **손상·만료된 저장분은 "없는 것"으로 취급하고 스스로 지운다** — `token-storage.test.ts`가 이 동작을 고정한다.

## 결과

- `web/next.config.ts` — rewrites와 그 이유가 주석으로
- **rewrites 목적지는 빌드 타임에 고정된다.** standalone 출력에 설정이
  직렬화되므로 런타임 환경변수로는 프록시 대상을 바꿀 수 없다(실제로
  Compose에서 `environment`로 넘겼다가 기본값 `127.0.0.1:8080`으로 500이
  나서 발견). 컨테이너 이미지는 `--build-arg API_PROXY_TARGET`으로 대상을
  굽고, 배포 대상이 바뀌면 재빌드한다. "설정은 런타임에"(12-factor)와
  어긋나는 지점이며, 배포 대상이 Compose 하나뿐인 현재로선 수용했다
- `web/src/lib/auth/token-storage.ts` — 보관 규율 + 테스트 5개
- CI Compose 단계가 `3000 → /api/v1/seasons → 200`으로 프록시 경유를 종단 검증

## 재검토 조건

- 토큰에 쓰기 권한이나 민감 정보 접근이 생기면 → (a) BFF 세션으로 이행한다. 그 시점의 이행 비용을 낮추기 위해 토큰 접근을 `token-storage.ts` 한 파일로 격리해 뒀다.
- 프론트를 CDN 정적 배포로 바꿔야 하면 → rewrites를 버리고 CORS 설정으로 돌아간다.
