# 08. 회고 — 2022년의 나에게 답장하기

> 이 회고는 **중간 회고**입니다. 규칙 엔진·서비스·릴리스까지(Step 0~4, 6)를 마친 시점에 쓰였고, P2의 최종 결론(CNN Grad-CAM 비교)과 절대 정확도는 Step 5 실행 후에만 말할 수 있습니다. 그때 §7이 갱신됩니다.

2022년의 결과보고서는 결론에 스스로의 한계를 적어두었습니다. 4년 뒤의 재구축은 그 문장에 대한 답장입니다 — 그래서 회고도 "무엇을 만들었나"가 아니라 **"그 한계들이 어떻게 됐나"** 부터 씁니다.

---

## 1. 세 문제는 어떻게 됐나

### P1 — 조도에 따라 판정이 흔들림 → 설계로 대응, 실측 검증은 미완

화이트밸런스 정규화를 전처리에 넣었습니다. 다만 여기서 이 프로젝트에서 가장 아끼는 판단 하나가 나왔습니다 — 초안은 "WB를 맨 앞에"였는데, 구현 중 측정으로 그 순서가 틀렸음을 발견했습니다. 전체 프레임 Gray-World는 얼굴이 프레임을 많이 차지할수록 **피부의 웜기 자체를 조명으로 오인해 지웁니다**(b\* 27.6 → 19.3). 문제를 고치려던 장치가 P1과 같은 성질의 새 편향을 만들고 있었습니다. 그래서 순서를 뒤집어 **얼굴을 제외한 배경으로만 조명을 추정**합니다 (ADR-004).

정직하게 남겨둘 것: 이 대응이 실제 사진의 조도 변화에서 판정을 얼마나 안정시키는지는 **아직 실측하지 않았습니다.** 검증셋에 "동일 인물, 다른 조명" 쌍을 의도적으로 포함하도록 설계해 둔 이유입니다 (02-data-pipeline.md §5).

### P2 — 얼굴 윤곽이 학습됨 → 서비스에서는 원천 차단, 원본 방식의 검증은 도구까지

서비스가 쓰는 규칙 엔진은 이 문제가 **구조적으로 불가능**합니다. 분류기 입력이 이미지가 아니라 (N,3) 피부 픽셀의 색채 통계 벡터라서, 얼굴형이 입력에 물리적으로 들어갈 수 없습니다. "윤곽을 학습하지 않도록 주의한다"가 아니라 **윤곽이 흐를 경로 자체를 제거**한 것이고, 이 차이가 재구축의 중심 아이디어입니다.

남은 것은 "원본 방식(이미지 입력 CNN)은 정말 윤곽을 봤는가"라는 검증입니다. 같은 데이터·구조·시드로 입력만 다른 두 모델(윤곽 포함 / 피부만)을 학습해 Grad-CAM을 나란히 놓는 실험 도구까지 만들었고, 합성 데이터로 종단 동작을 확인했습니다. **결론은 실데이터 학습 후에** — 여기서 미리 말하지 않습니다.

### P3 — 라벨 오염 → 오염원을 제거하고, 단어부터 구분

크롤링 검색어 라벨을 버렸습니다. 대신 규칙 엔진이 라벨을 만들고(pseudo-label), 절대 기준은 수동 검증셋이 맡습니다. 그리고 코드·리포트·문서가 **"정확도"와 "일치율(agreement)"을 단어부터 구분**합니다 — pseudo-label 기준 수치는 "규칙 엔진을 얼마나 복제했나"일 뿐입니다. 원본이 오염된 라벨 위의 82%를 정확도라 불렀던 것에 대한 직접적인 교정입니다.

## 2. 원본에게 배운 것 — 가장 큰 손실은 코드가 아니라 근거였다

원본의 소스는 git을 쓰지 않아 유실됐습니다. 그런데 재구축을 하며 알게 된 진짜 손실은 코드가 아니었습니다. 보고서와 발표자료로 파이프라인은 복원할 수 있었지만, **"왜 그렇게 했는가"는 어디에도 없었습니다.** YCrCb 범위는 왜 그 값이었는지, Otsu와의 교집합은 누구의 아이디어였는지, 82%는 어떤 분할에서 나왔는지 — 전부 사라졌습니다.

그래서 이번엔 반대로 걸었습니다. 결정마다 ADR(9건), 기각한 대안과 그 이유, 임계값마다 근거 docstring, 그리고 그 근거가 틀렸을 때의 기록까지. **코드보다 결정의 근거가 더 오래 살아남게** 만드는 것이 이 저장소의 방침이고, 4년 전의 유실이 그 방침의 이유입니다.

원본이 잘한 것도 그대로 인정하고 계승했습니다 — YCrCb ∧ Otsu 교집합 마스킹은 지금 봐도 좋은 아이디어라 재구축 파이프라인에 살아 있습니다.

## 3. 잘했다고 생각하는 판단 셋

**경계를 "측정된 것"과 "우리가 정한 것" 사이에 그은 것** (ADR-005). 측정·판정은 Python이, 팔레트·라벨 같은 큐레이션은 Spring+DB가 소유합니다. 이 경계 덕에 "봄 웜에 코랄 대신 살구"라는 큐레이션 변경이 추론 서버 재배포를 요구하지 않고, 경계가 조용히 무너지지 않도록 양쪽 테스트가 지킵니다.

**실패의 정의를 명시적으로 설계한 것.** 서킷 브레이커가 `ImageRejectedException`(얼굴 없음)을 실패로 세지 않습니다 — 그건 측정기가 정상 동작한 결과입니다. 이 구분은 UI까지 일관됩니다: "사진을 바꾸면 되는 실패"와 "서비스 문제"는 다른 화면을 받습니다.

**정직성을 규율이 아니라 시스템으로 만든 것.** 측정이 주장을 반증하면 주장을 고친 실제 사례(Haar 오검출 주장 철회), Phase 3 전 정확도 언급 금지, 미측정 항목의 명시, "일치율"이라는 단어 선택 — 개별 사건이 아니라 저장소 전반의 동작 방식입니다. 포트폴리오로서도 이것이 가장 강한 서사라고 판단합니다: "모델을 만들었다"보다 "모델이 정말 필요한지 측정할 준비를 했다"가 더 방어 가능한 주장입니다.

## 4. 아쉬운 것, 다시 한다면

**아직 정확도를 한 번도 말하지 못했습니다.** 원칙을 지킨 결과이지만, 뒤집어 말하면 이 서비스가 실제로 잘 맞는지 **모른다**는 뜻입니다. 검증셋 라벨링(수작업 200~300장)을 로드맵 뒤로 미룬 것이 병목이 됐습니다. 다시 한다면 Step 1 직후부터 사진을 모으기 시작했을 겁니다 — 도구는 하루면 만들지만 데이터는 기다려주지 않습니다.

**실사진 검증이 전반적으로 부족합니다.** 파이프라인·API·학습 하네스 모두 합성 얼굴로 검증했습니다. 회귀는 잡아주지만, 마스킹 임계값·coverage_ratio의 실제 분포, 회전 강건성 같은 보정 근거는 실사진이 있어야 나옵니다.

**E2E 테스트가 없습니다.** 브라우저 플로우는 개발 중 자동화로 확인했지만 회귀 스위트에는 없습니다. 다섯 서비스 Compose 종단 검증이 그 자리의 절반을 메우고 있을 뿐입니다.

**운영 데이터가 없습니다.** 실서버 배포를 하지 않기로 하면서(비용 대비 가치) 부하·지연·실사용 패턴 같은 운영 서사는 얻지 못했습니다. 관측성(상관관계 ID·구조화 로그)을 만들어 두고도 그것이 실전 트래픽을 본 적이 없다는 점은, 포트폴리오 문답에서 그대로 인정할 부분입니다.

## 5. 수치로 보는 대비

| | 원본 (2022) | 재구축 (2026) |
|---|---|---|
| 소스 보존 | 유실 (git 미사용) | 전부 + CI가 커밋마다 검증 |
| 결정 기록 | 결과보고서 1부 | ADR 9건 + 설계 문서 10건 |
| 테스트 | 언급 없음 | 277개 (Java 141 · Python 111 · TS 25) |
| 판정 근거 노출 | 라벨 하나 | 확률 분포 + 3축 측정값 + 전처리 보고 |
| 라벨 출처 | 검색어 (오염) | 규칙 엔진 pseudo + 수동 검증셋 (예정) |
| 정확도 주장 | val_accuracy 0.82 | **보류** — 검증셋 평가 전까지 말하지 않음 |

마지막 줄이 이 표의 요점입니다. 숫자가 없는 칸이 후퇴가 아니라 **교정**이라는 것 — 그것이 이 재구축이 원본에게 하는 답장입니다.
